# Requirements Specification

Maintained requirements derived from the research in
[docs/research/download-manager-rnd-bn.md](docs/research/download-manager-rnd-bn.md) (cited as §N).
When sections conflict, the later corrections take precedence: §14.4, §15, §16.2, §17 and §18.

The research describes proposals. This file records **accepted requirements**. Implementation and
verification status are tracked separately, both here and in [docs/traceability.md](docs/traceability.md).
Nothing in this file claims that a feature works until its status is `verified` and evidence is linked.

## Conventions

**Status** (exactly one per requirement):

| Status | Meaning |
|---|---|
| `proposed` | In research, needs a spike/decision before it is committed to a milestone |
| `documented` | Accepted and specified; no implementation yet |
| `in-progress` | Some code exists, but the acceptance criteria are not yet met or not yet checked |
| `implemented` | Code meets the acceptance criteria by inspection; evidence incomplete (e.g. one OS only) |
| `verified` | Acceptance evidence recorded in docs/traceability.md (test, fixture report, OS run) |
| `blocked` | Cannot proceed; blocker recorded in PROGRESS.md |
| `deferred` | Accepted but intentionally scheduled after the current release scope |

**Priority:** P0 = before public beta (foundation/correctness). P1 = desktop increment after the baseline is stable. P2 = separate large module (§17).

**Milestones** ([docs/roadmap.md](docs/roadmap.md)): B0 architecture gate · B1 reliable core · B2 desktop and extension ·
B3 public beta · B4 advanced desktop (MVP+/V1) · B5 media and extensibility · B6 optional ecosystem (V2) · B7 mobile.

Research phase labels map to milestones as follows: MVP+ → B4, V1 → B4 (media V1 items → B5), V2 → B6.

Requirement IDs are stable. Never renumber them. Retire an ID by setting it to `deferred` with a note, never by deleting it.
F01–F16, E01–E06 and ADV01–ADV12 keep the IDs used in the research.

## 1. Architecture constraints

### ARCH-01 — Separate per-user download service
- **Outcome:** Downloads continue when the UI window closes, the UI crashes, or the browser closes. They stop only on an explicit stop.
- **Priority:** P0 · B0
- **Depends on:** —
- **Acceptance:** The service runs as a separate process under the current OS user, not elevated. There is one service instance per user. Closing or killing the UI or the browser does not stop active transfers. "Exit and stop downloads" checkpoints and stops them. A test covers each case on all three desktop OSes.
- **Source:** §5, §15.2, §15.3
- **Status:** `in-progress`

### ARCH-02 — File bytes flow origin → backend → disk
- **Outcome:** Large files never pass through the UI, the browser bridge or any project server, so neither memory use nor privacy depends on them.
- **Priority:** P0 · B0
- **Depends on:** ARCH-01
- **Acceptance:** No API, IPC message or native-messaging message carries file content. The backend writes directly to the destination volume. A code review checklist and an IPC schema check (no byte payload fields) enforce this.
- **Source:** §4, §5, §15.3, §15.7
- **Status:** `documented`

### ARCH-03 — Replaceable download backend; service-owned job identity
- **Outcome:** The engine can be replaced (aria2 → patched/custom) without changing UI, database or API.
- **Priority:** P0 · B0
- **Depends on:** ARCH-01
- **Acceptance:** The service talks to engines only through the `DownloadBackend` trait. Job IDs (`job_…`) and attempt IDs (`att_…`) are generated by the service. aria2 GIDs exist only inside the backend adapter's attempt mapping. They are never persisted as job identity and never appear in UI, CLI or contracts. A contract test rejects a GID used as a job ID.
- **Source:** §15.2, §15.3, §18.1
- **Status:** `implemented`

### ARCH-04 — Explicit backend capability reporting
- **Outcome:** Users see what is actually supported. An unsupported feature fails clearly instead of degrading silently.
- **Priority:** P0 · B0
- **Depends on:** ARCH-03
- **Acceptance:** Every backend returns a report covering all `Capability` values, each marked `supported`, `unsupported` or `unverified`. A capability is `supported` only after project fixtures prove it. Features gate on `supported` and otherwise return `BACKEND_CAPABILITY_UNAVAILABLE`. Example: an unsupported proxy profile never falls back to a direct connection. The report is visible through `service.v1.hello`.
- **Source:** §14.1 (note), §14.3, §15.2, §16.2
- **Status:** `implemented`

### ARCH-05 — Single SQLite writer; engine owns segment state
- **Outcome:** Restart recovery has exactly one source of truth for byte progress, so no conflicting state can corrupt it.
- **Priority:** P0 · B1
- **Depends on:** ARCH-01, ARCH-03
- **Acceptance:** Only the service process opens SQLite for writing. The schema has no segment byte map. `resume_checkpoints` stores only a versioned reference to engine-owned state. Restart reconciliation compares the engine session/control file, the actual partial file and the job list.
- **Source:** §5, §15.2, §17.4, §18.3
- **Status:** `documented`

### ARCH-06 — Local, authenticated, versioned control IPC
- **Outcome:** Web pages, other users and remote hosts cannot control downloads.
- **Priority:** P0 · B0
- **Depends on:** ARCH-01
- **Acceptance:** The UI, CLI and native host reach the service through a Windows named pipe or Unix-domain socket that only the current user can access, using JSON-RPC 2.0 with versioned methods (`downloads.v1.*`). aria2 RPC binds to loopback with a random secret and is used only by the backend adapter. Neither the renderer nor web pages can reach engine RPC. There is no arbitrary aria2 option passthrough.
- **Source:** §5, §14.3, §18.2
- **Status:** `implemented`

### ARCH-07 — One shared contract for UI, CLI, browser host and extension
- **Outcome:** Every client sees the same state and behaviour, with no second implementation.
- **Priority:** P0 · B0
- **Depends on:** —
- **Acceptance:** `packages/contracts/schema/service-api.v1.schema.json` is the canonical source. TypeScript types are generated from it. The Rust mirror (`dm-domain::api`) round-trips every example. `pnpm contracts:check` and `cargo test -p dm-domain` fail on drift. Byte counts are decimal strings, IDs are strings, unknown size is `null`.
- **Source:** §15.3, §18.2
- **Status:** `verified`

### ARCH-08 — Coalesced, resumable event stream
- **Outcome:** The UI stays responsive with many active downloads, and a slow UI cannot stall transfers.
- **Priority:** P0 · B2
- **Depends on:** ARCH-06, ARCH-07
- **Acceptance:** Progress events are coalesced to a 250–500 ms starting target. Semantic state changes are sent immediately. Each event carries `service_instance_id`, `sequence`, `job_id` and `attempt_id`. A sequence gap or a new instance ID causes the client to request a fresh snapshot. A slow consumer is dropped or resnapshotted and never blocks the service.
- **Source:** §15.4, §18.2
- **Status:** `documented`

### ARCH-09 — Defined lifecycle for seven cases
- **Outcome:** The behaviour in each lifecycle case is predictable and documented.
- **Priority:** P0 · B2
- **Depends on:** ARCH-01
- **Acceptance:** Behaviour is documented and tested for each of: UI close, browser close, native-host disconnect, service restart, OS logout, OS sleep and reboot. The scheduler does not promise to run while the computer is off. The missed-schedule policy ("run now" or "next window") is explicit.
- **Source:** §5, §15.3
- **Status:** `documented`

### ARCH-10 — Architecture changes require an ADR
- **Outcome:** Major decisions stay traceable and consistent across documents.
- **Priority:** P0 · B0
- **Depends on:** —
- **Acceptance:** Replacing a decision in ADR 0001, or any later ADR, requires a new ADR under `docs/decisions/` and updates to every affected document in the same change.
- **Source:** Foundation brief; §15.2 (engine replacement criteria)
- **Status:** `implemented`

## 2. Baseline download features

### CORE-01 — Add HTTP/HTTPS download by URL
- **Outcome:** The user pastes a link and gets the file.
- **Priority:** P0 · B0 (CLI), B2 (UI)
- **Depends on:** ARCH-03, ARCH-06, COR-09
- **Acceptance:** `downloads.v1.add` accepts http(s) URLs with a destination profile and rejects other schemes with `INVALID_REQUEST`. A controlled fixture download completes and its file hash matches the expected value. The UI and CLI use the same method.
- **Source:** §6 (1), §15.8
- **Status:** `in-progress`

### CORE-02 — Segmented download when the server supports it
- **Outcome:** Faster downloads where a server and network allow it, without overloading hosts.
- **Priority:** P0 · B1
- **Depends on:** COR-01, E03
- **Acceptance:** Range capability is decided from the actual 206 response and Content-Range, never from Accept-Ranges alone. Small files use a single connection. Starting policy: 2–4 connections for large range-capable files, at most 8 per host across all jobs, and 3 active files. Speed-up claims require REL-04 benchmarks.
- **Source:** §6 (2), §7, §15.4
- **Status:** `in-progress`

### CORE-03 — Pause, resume, cancel, retry
- **Outcome:** The user controls every download, and their intent is never overridden.
- **Priority:** P0 · B0
- **Depends on:** ARCH-03, COR-07
- **Acceptance:** Each command changes `desired_state` and returns an acknowledgement. Cancel is acknowledged only after the workers stop and ownership is invalidated. Retry creates a new attempt. Resume obeys COR-01/COR-02.
- **Source:** §6 (3), §18.2
- **Status:** `in-progress`

### CORE-04 — Restart and crash recovery
- **Outcome:** After an app crash, kill or reboot, supported downloads continue without corruption.
- **Priority:** P0 · B1
- **Depends on:** ARCH-05, ADV06
- **Acceptance:** Kill tests for the service, the engine and the UI, repeated N times, never produce a corrupt "completed" file. Supported jobs resume. Unsupported jobs show an explicit reason.
- **Source:** §6 (3), §7, §11, §15.9
- **Status:** `documented`

### CORE-05 — Multiple queues and priority
- **Outcome:** The user organises work, for example "Study" and "Night".
- **Priority:** P0 · B2
- **Depends on:** CORE-03
- **Acceptance:** The user can create, rename and delete queues and reorder jobs. Priority affects start order. The active-file limit is respected per queue and globally.
- **Source:** §6 (4), §15.6
- **Status:** `documented`

### CORE-06 — Global and per-download speed limits
- **Outcome:** Downloads do not saturate the user's connection.
- **Priority:** P0 · B3
- **Depends on:** ARCH-04
- **Acceptance:** Limits are applied and visible in the UI. Measured throughput stays within ±10% of the limit on the controlled fixture. Limits are gated on the backend reporting the capability.
- **Source:** §6 (4), §15.2
- **Status:** `documented`

### CORE-07 — Categories, destination rules, filename conflicts, duplicates
- **Outcome:** Files land in the right folder and existing files are never overwritten.
- **Priority:** P0 · B2
- **Depends on:** E04
- **Acceptance:** Category to folder mapping works. A name collision produces a new name or asks the user and never overwrites. A duplicate URL triggers a prompt showing the existing job.
- **Source:** §6 (5), §16.1
- **Status:** `documented`

### CORE-08 — Scheduler
- **Outcome:** Downloads run in a chosen time window while the app is running.
- **Priority:** P0 · B3
- **Depends on:** COR-07, ARCH-09
- **Acceptance:** A schedule (timezone, window, eligible queue) adds a `schedule_window` blocker outside the window. Missed runs follow the configured policy. The UI states that schedules do not run while the computer is off or asleep.
- **Source:** §5, §6 (6), §15.3
- **Status:** `documented`

### CORE-09 — Completion notification
- **Outcome:** The user knows when a file is ready, or why it failed.
- **Priority:** P0 · B3
- **Depends on:** ADV06
- **Acceptance:** An OS notification fires only after the job reaches `completed` (after verification and finalization) or `failed`. Notifications can be turned off.
- **Source:** §6 (6)
- **Status:** `documented`

### CORE-10 — History and search
- **Outcome:** The user finds past downloads.
- **Priority:** P0 · B2
- **Depends on:** ARCH-05
- **Acceptance:** History is searchable by name and domain. "Clear list" and "delete file" are separate, explicitly labelled actions. A retention policy exists.
- **Source:** §6 (8), §18.3
- **Status:** `documented`

### CORE-11 — Clear, classified error messages
- **Outcome:** The user understands what went wrong and what to do next.
- **Priority:** P0 · B1
- **Depends on:** ARCH-07
- **Acceptance:** Every failure maps to a stable `ErrorKind` with `retryable` and `next_action` fields. Fixtures prove a correct classification for expired link, no-resume server, disk full, auth required and remote changed. Copy exists in both English and Bangla.
- **Source:** §6 (8), §15.6, §17.6
- **Status:** `in-progress`

## 3. Correctness

### COR-01 — Validated range responses only
- **Outcome:** A resumed or segmented file is never a mix of wrong bytes.
- **Priority:** P0 · B1
- **Depends on:** ARCH-03
- **Acceptance:** Partial bytes are appended only on a 206 with a Content-Range that matches the request. A 200 to a range request never appends: it restarts safely or fails. Fixtures cover range-ignored, wrong Content-Range and short body. If aria2 cannot guarantee this, the B0 go/no-go decision records a patch, wrapper or replacement.
- **Source:** §7, §15.4, §16.2, §18.5
- **Status:** `implemented`

### COR-02 — Representation identity before resume
- **Outcome:** If the remote file changed, the download never silently continues with old bytes.
- **Priority:** P0 · B1
- **Depends on:** COR-01, ADV06
- **Acceptance:** Only a strong ETag (or equivalent trusted content identity) is used for If-Range. A weak ETag never is. Equal length is not proof of identity. aria2 `conditional-get` (If-Modified-Since) is not treated as a resume guarantee. A changed or missing validator leads to a safe restart or a `REMOTE_CHANGED` decision. Fixtures cover same-length changed content and changed, weak and missing ETags.
- **Source:** §7, §15.4, §16.2
- **Status:** `implemented`

### COR-03 — Edge responses: 416, truncated, unknown size, zero bytes, encoding
- **Outcome:** Unusual server behaviour never produces a false success.
- **Priority:** P0 · B1
- **Depends on:** COR-01
- **Acceptance:** Distinct branches exist for 416, a truncated body, unknown total (sequential fallback), zero-byte files and a changed Content-Encoding. Encoded and decoded offsets are never mixed. Each branch has a fixture.
- **Source:** §7, §14.4, §16.2, §17.4
- **Status:** `in-progress`

### COR-04 — Retry and backoff policy
- **Outcome:** Downloads recover from transient errors without hammering servers or retrying failed logins.
- **Priority:** P0 · B1
- **Depends on:** CORE-11
- **Acceptance:** Bounded exponential backoff with jitter. 429 and 503 honour Retry-After and add a `rate_limit_cooldown` blocker. Authentication failures and permanent errors are not retried automatically. A 403 or 410 is classified as auth, revoked or link refresh, never assumed to mean "expired".
- **Source:** §7, §15.4, §16.2
- **Status:** `implemented`

### COR-05 — Checksum verification
- **Outcome:** The user can confirm a file matches what the publisher intended.
- **Priority:** P0 · B1
- **Depends on:** ADV06
- **Acceptance:** When a trusted expected SHA-256 is given, completion requires a match. A mismatch gives `CHECKSUM_MISMATCH` and never `completed`. The UI distinguishes a "publisher checksum matched" result from a "locally computed hash".
- **Source:** §7, §16.1
- **Status:** `documented`

### COR-06 — Safe link replacement
- **Outcome:** Replacing an expired link keeps progress only when that is provably safe.
- **Priority:** P0 · B1
- **Depends on:** COR-02
- **Acceptance:** `downloads.v1.replaceSource` re-validates resource identity. On a match it keeps the progress. On a mismatch or with no validator it offers restart or keep (`choose_restart_or_keep`). Same-length changed content is detected by a fixture.
- **Source:** §6 (value table), §15.6, §18.2
- **Status:** `documented`

### COR-07 — Desired state, phase and blockers kept separate
- **Outcome:** A manual pause is never undone by a network reconnect or schedule change.
- **Priority:** P0 · B0
- **Depends on:** —
- **Acceptance:** The domain model has independent `DesiredState`, `Phase` and `Blocker` set. Precedence: cancel → user pause → disk → network/schedule → queue. Clearing blockers releases only policy-held jobs. Unit tests cover "user pause + reconnect".
- **Source:** §17.1, §17.4, §18.5
- **Status:** `verified`

### COR-08 — Durability ordering
- **Outcome:** A power loss or crash cannot make metadata claim more progress than is actually on disk.
- **Priority:** P0 · B1
- **Depends on:** ARCH-05
- **Acceptance:** Live progress is kept separate from durable checkpoints. The proposed SQLite mode is WAL + synchronous=FULL, with its cost benchmarked. A documented flush and checkpoint order is followed, and a fault test kills the process during a checkpoint.
- **Source:** §14.3, §16.2, §17.4
- **Status:** `documented`

### COR-09 — Idempotent job creation
- **Outcome:** A lost acknowledgement or a double click never creates duplicate downloads.
- **Priority:** P0 · B0
- **Depends on:** ARCH-07
- **Acceptance:** The same idempotency key with the same request fingerprint returns the same job. The same key with a different payload returns `IDEMPOTENCY_CONFLICT`. Records are durable with bounded retention. A test simulates an extension retry after a lost acknowledgement.
- **Source:** §17.5, §18.2, §18.3
- **Status:** `in-progress`

## 4. Browser integration

### BRW-01 — Chrome/Edge "Download with…" for public GET links
- **Outcome:** One click from the browser hands a link to the app.
- **Priority:** P0 · B2
- **Depends on:** BRW-02, CORE-01
- **Acceptance:** The context-menu action works on Chrome and Edge for public HTTP(S) GET links on all three desktop OSes, end to end (browser → host → service → file hash).
- **Source:** §6 (7), §8, §15.5
- **Status:** `documented`

### BRW-02 — Small native messaging host
- **Outcome:** The browser can talk to the app safely.
- **Priority:** P0 · B2
- **Depends on:** ARCH-06
- **Acceptance:** The host validates framing, sender origin and payload against the contracts, and forwards requests to the service. It never transfers file bytes. Browser exit or host exit never stops transfers. Large payloads are rejected.
- **Source:** §5, §15.3, §18.1
- **Status:** `documented`

### BRW-03 — Handoff with acknowledgement and fallback
- **Outcome:** A browser download is never lost when the app is missing or unsuitable.
- **Priority:** P0 · B2
- **Depends on:** BRW-02, COR-09
- **Acceptance:** For a supported request, the browser download is cancelled only after native readiness or acceptance. If the host is missing, times out or the request is unsupported, the browser download continues. "Accepted" and "transfer established" are reported as separate statuses. Missing-host and timeout tests pass.
- **Source:** §14.4, §15.5, §16.2, §17.5
- **Status:** `documented`

### BRW-04 — Optional automatic capture
- **Outcome:** Ordinary browser downloads go to the app automatically when the user enables it.
- **Priority:** P1 · B2
- **Depends on:** BRW-03, E02
- **Acceptance:** Off by default. When enabled it uses the downloads API with MIME, extension, size and site filters and native acknowledgement. It does not rely on MV3 webRequestBlocking.
- **Source:** §8, §15.5
- **Status:** `documented`

### BRW-05 — Authenticated downloads with scoped context
- **Outcome:** Login-protected files work where safely possible, without leaking sessions.
- **Priority:** P1 · B3
- **Depends on:** BRW-03, SEC-02
- **Acceptance:** Cookie access needs an explicit permission and a user action, and is scoped to the origin, cookie store and partition. Credential scope is checked at every redirect hop and never forwarded cross-origin. A partition or profile mismatch returns an actionable "unsupported" result. Compatibility is never claimed as universal.
- **Source:** §8, §15.5, §17.5
- **Status:** `documented`

### BRW-06 — Browser-only requests stay in the browser
- **Outcome:** POST exports, blob/data URLs and single-use links are never broken by takeover.
- **Priority:** P0 · B2
- **Depends on:** BRW-03
- **Acceptance:** POST, blob:, data: and browser-generated downloads are never sent to the engine as a remote URL. The browser flow continues. Tests cover each category.
- **Source:** §8, §15.5, §16.2
- **Status:** `documented`

### BRW-07 — Host registration, repair and uninstall
- **Outcome:** Installing, updating or moving the app keeps the browser connection working.
- **Priority:** P0 · B2
- **Depends on:** BRW-02, REL-01
- **Acceptance:** Per-browser registration is handled: Chrome `allowed_origins` versus Firefox `allowed_extensions`, the Windows registry, and macOS/Linux manifest paths. Store and development IDs are both handled. AppImage uses a stable installed host path. A repair action exists. Uninstall removes only the app's own registrations.
- **Source:** §15.5, §17.9
- **Status:** `documented`

### BRW-08 — Firefox support
- **Outcome:** Firefox users get the same supported flows.
- **Priority:** P1 · B3
- **Depends on:** BRW-01, BRW-07
- **Acceptance:** A separate manifest and compatibility validation pass the BRW-01/03/06 tests on Firefox.
- **Source:** §8, §15.1
- **Status:** `documented`

### BRW-09 — Snap/Flatpak browsers as a separate category
- **Outcome:** Linux users get an honest support statement.
- **Priority:** P1 · B3
- **Depends on:** BRW-07
- **Acceptance:** Portal/native-proxy availability is tested per package. Support is published per package type. "Ubuntu support" is never taken to imply sandboxed-browser support.
- **Source:** §15.5
- **Status:** `documented`

### BRW-10 — Incognito capture disabled by default
- **Outcome:** Private browsing is not recorded unexpectedly.
- **Priority:** P0 · B2
- **Depends on:** BRW-04
- **Acceptance:** Capture is off in incognito by default. Enabling it shows the ephemeral session and history policy.
- **Source:** §17.5
- **Status:** `documented`

### BRW-11 — Safari extension
- **Outcome:** Safari users can hand off downloads.
- **Priority:** P2 · B6
- **Depends on:** BRW-07
- **Acceptance:** A separate macOS extension project with its own feasibility decision.
- **Source:** §8, §15.1
- **Status:** `deferred`

## 5. Desktop UI

### UI-01 — English and Bangla interface
- **Outcome:** Bangla-speaking users can use the app comfortably.
- **Priority:** P0 · B3
- **Depends on:** —
- **Acceptance:** Every UI string exists in `en` and `bn` (enforced by type). The document `lang` follows the locale. Bangla line height and fonts follow design.md. Bangla copy has a localisation QA pass before beta.
- **Source:** §6 (9), §11, §15.6
- **Status:** `in-progress`

### UI-02 — Light and dark themes through semantic tokens
- **Outcome:** The app is comfortable in any lighting and respects OS settings.
- **Priority:** P0 · B2
- **Depends on:** —
- **Acceptance:** Default is system theme, with Light and Dark overrides. Components use only tokens. Forced-colors and reduced-motion are respected. Contrast reaches WCAG 2.2 AA for text and focus indicators (audit before beta).
- **Source:** §6 (9), §14.1 (F16)
- **Status:** `in-progress`

### UI-03 — Honest, distinct status presentation
- **Outcome:** The user is never misled about whether a file is ready.
- **Priority:** P0 · B2
- **Depends on:** ARCH-07, COR-07
- **Acceptance:** Paused (user), held (policy, with reason), failed (kind + next action), cancelled, verifying, scanning and completed are visually and textually distinct in both languages, and colour is never the only cue. The service-unavailable state is explicit.
- **Source:** §11 (release gates), §17.4
- **Status:** `in-progress`

### UI-04 — Close-to-tray and explicit exit
- **Outcome:** The user decides whether closing the window stops downloads.
- **Priority:** P0 · B2
- **Depends on:** ARCH-01, ARCH-09
- **Acceptance:** A clear setting controls close behaviour. The tray offers "Open" and "Exit and stop downloads". The UI never kills the service implicitly.
- **Source:** §5
- **Status:** `documented`

## 6. Privacy and security

### SEC-01 — Secrets never in logs, exports, history or engine config
- **Outcome:** Session cookies and tokens cannot leak through support files.
- **Priority:** P0 · B0
- **Depends on:** —
- **Acceptance:** URLs are redacted (userinfo, query values, fragment) before logging or display. Cookie, Authorization and proxy credentials are wrapped in a non-serializable `Secret`. A synthetic-secret test proves absence from logs, events, diagnostics exports, the SQLite history and the aria2 session/config files.
- **Source:** §10, §14.3, §17.5, §17.6
- **Status:** `in-progress`

### SEC-02 — OS credential store for secrets
- **Outcome:** Stored credentials have OS-level protection.
- **Priority:** P0 · B3
- **Depends on:** SEC-01
- **Acceptance:** Proxy passwords and other persisted secrets live in Windows Credential Manager, macOS Keychain or the Linux Secret Service. SQLite stores only references. The UI never receives engine secrets.
- **Source:** §4, §5, §18.3
- **Status:** `documented`

### SEC-03 — Never auto-execute downloads
- **Outcome:** A downloaded executable cannot run without the user acting.
- **Priority:** P0 · B2
- **Depends on:** —
- **Acceptance:** No code path opens or executes a downloaded file automatically. "Open" requires a user action.
- **Source:** §10
- **Status:** `documented`

### SEC-04 — Free, account-free, no ads or tracking
- **Outcome:** Core features work offline, forever, without sign-in.
- **Priority:** P0 · B0
- **Depends on:** —
- **Acceptance:** A clean install works offline with no account for download, queue, scheduler, browser integration and history. There is no telemetry by default. Crash reports are opt-in with a local preview (E05).
- **Source:** §1, §6, §10, §15.7
- **Status:** `documented`

### SEC-05 — Scoped desktop command surface
- **Outcome:** A compromised web content process cannot misuse the desktop shell.
- **Priority:** P0 · B2
- **Depends on:** ARCH-06
- **Acceptance:** Tauri capabilities grant only the needed permissions. Each custom command validates its input in Rust. A strict CSP is set. There is no remote content.
- **Source:** §17.7 (S41)
- **Status:** `in-progress`

## 7. Release, platforms and licensing

### REL-01 — Per-OS installers with clean install, update and uninstall
- **Outcome:** Users can install and remove the app reliably.
- **Priority:** P0 · B0 (smoke), B3 (beta)
- **Depends on:** —
- **Acceptance:** Windows 10/11 x64 installer, macOS 13+ build (Intel and Apple Silicon), and Ubuntu 22.04/24.04 x64 DEB, then AppImage. Install, update and uninstall leave no orphan processes or registrations, and they preserve user downloads.
- **Source:** §3, §6 (10), §15.1, §15.9
- **Status:** `in-progress`

### REL-02 — Platform support claimed only with evidence
- **Outcome:** Users can trust the published support matrix.
- **Priority:** P0 · B3
- **Depends on:** REL-01
- **Acceptance:** An OS, browser or package is labelled "supported" only after installer and real-device tests pass and the evidence is recorded in traceability. Everything else is "untested" or "unsupported".
- **Source:** §3, §15.1
- **Status:** `documented`

### REL-03 — Dependency licensing compliance
- **Outcome:** Distribution is legally sound.
- **Priority:** P0 · B3
- **Depends on:** ADV09
- **Acceptance:** Releases bundle the aria2 GPL-2.0-or-later notices and an offer or link for the exact corresponding source. Third-party notices are included. Dependency versions are pinned. The project license is decided after a dependency audit (an open decision in ADR 0001).
- **Source:** §10, §14.4, §15.7, §16.2
- **Status:** `documented`

### REL-04 — Fair, reproducible benchmarks before claims
- **Outcome:** Any speed or memory claim is honest.
- **Priority:** P0 · B3
- **Depends on:** CORE-02
- **Acceptance:** Same device, server and network profile. No concurrent apps. At least 5 rotated runs with medians, and at least 20 runs for p95. Measurements cover the full process tree (UI, webview, service, engine). Scripts and raw results are published. No claim is made without them.
- **Source:** §11, §15.9
- **Status:** `documented`

### REL-05 — Pinned, provenance-tracked engine sidecar
- **Outcome:** The bundled engine is current and auditable.
- **Priority:** P0 · B0
- **Depends on:** ARCH-03
- **Acceptance:** The aria2 version is pinned per OS, with its source/build provenance and TLS library version recorded. No unmaintained binaries are bundled blindly.
- **Source:** §15.2
- **Status:** `in-progress`

## 10. Extended details from §14.2 (E01–E06)

### E01 — Media pipeline: quality picker, audio-only, merge, subtitles
- **Outcome:** Users can download supported media in a chosen format.
- **Priority:** P2 · B5
- **Depends on:** ARCH-04, ADV06
- **Acceptance:** Persisted stages: extract, select, fetch, mux, validate, finalize. A failed mux reuses the verified inputs. FFmpeg and yt-dlp run with argument arrays, stdin off, restricted protocols, and limits on time and output size. DRM-protected content is out of scope and shows a clear status. Encrypted HLS (AES-128) is classified separately from DRM.
- **Source:** §9, §14.2, §17.8
- **Status:** `deferred`

### E02 — Browser capture filters and Opera QA
- **Outcome:** Users control which browser downloads are captured.
- **Priority:** P1 · B2 (filters), B4 (Opera, Brave and Vivaldi QA)
- **Depends on:** BRW-04
- **Acceptance:** MIME, extension, size and site-exclusion filters. Referrer, user-agent and session handling is domain-scoped. Opera compatibility is published only after testing.
- **Source:** §14.2, §15.1
- **Status:** `documented`

### E03 — Per-host connection budget and split policy
- **Outcome:** Downloads are fast without abusing servers.
- **Priority:** P0 · B1 (budget), B4 (dynamic scheduling, see ADV02)
- **Depends on:** CORE-02
- **Acceptance:** The host connection budget is counted across all jobs. Small ranges are not split. HTTP/2 or HTTP/3 needs a separate transport feasibility decision, because aria2 documents HTTP/1.1 only.
- **Source:** §14.2, §15.4, §16.1
- **Status:** `documented`

### E04 — Allocation, filesystem limits and filename normalisation
- **Outcome:** Files are named safely and correctly on every OS.
- **Priority:** P0 · B1
- **Depends on:** ADV05
- **Acceptance:** Content-Disposition and `filename*` (RFC 6266) are parsed, and the server name is treated as advisory. Separators, control characters and reserved names (CON, NUL, …) are normalised. Long Unicode and Bangla names, filesystem size limits and invalid paths have tests. The allocation policy is documented.
- **Source:** §14.2, §14.3
- **Status:** `in-progress`

### E05 — Redacted diagnostic export
- **Outcome:** Users can share a support file without leaking secrets.
- **Priority:** P0 · B3
- **Depends on:** SEC-01, ADV07
- **Acceptance:** Crash reports are opt-in with a local preview. Export works offline. Tokens, cookies and headers are redacted, proven by a synthetic-secret test. There is no analytics gating.
- **Source:** §14.2, §17.6
- **Status:** `documented`

### E06 — Verification and scanning lifecycle states
- **Outcome:** Users know a file is still being checked.
- **Priority:** P0 · B3
- **Depends on:** ADV06
- **Acceptance:** `scanning`, `blocked` and `scan-unavailable` are reported identically in the UI and the CLI. A scan failure is never shown as "verified safe".
- **Source:** §14.2
- **Status:** `documented`

## 11. Advanced workflows from §17 (ADV01–ADV12)

### ADV01 — Metered network and Data Saver profile
- **Outcome:** Large downloads defer or slow down on a hotspot.
- **Priority:** P1 · B4
- **Depends on:** COR-07, platform adapters
- **Acceptance:** A manual pause never auto-resumes on reconnect. An unknown network state is visible. The user profile overrides OS hints (Windows ConnectionCost, macOS NWPath expensive/constrained, NetworkManager metered). The data counter is labelled approximate.
- **Source:** §17, §17.1
- **Status:** `documented`

### ADV02 — Adaptive per-host tuning and fair bandwidth
- **Outcome:** One file or host cannot starve the others.
- **Priority:** P1 · B4
- **Depends on:** E03
- **Acceptance:** The shared host budget is never exceeded. Trials use 1/2/4/8 connections and keep only measured benefit. Pressure is reduced on 429. Observation keys exclude cookies and raw signed URLs. How far the aria2 adapter can control this is checked in a spike.
- **Source:** §17, §17.1
- **Status:** `documented`

### ADV03 — Declarative automation rules with preview
- **Outcome:** Folder, queue and limit are chosen automatically by domain, type or size.
- **Priority:** P1 · B4
- **Depends on:** CORE-07
- **Acceptance:** Rules are ordered with defined stop semantics. A dry-run shows which rule matched and why. Unknown MIME or size shows "pending/unknown" and never triggers a destructive move. Active or completed jobs change only with explicit user action.
- **Source:** §17, §17.2
- **Status:** `documented`

### ADV04 — Portable download-set export and import
- **Outcome:** Users can move a download list to another PC.
- **Priority:** P1 · B4
- **Depends on:** F04, SEC-01
- **Acceptance:** Versioned JSON with schema validation and a preview. Credentials, absolute paths and sensitive signed queries are excluded, with such items set to needs_link_refresh. Import enforces item-count and size limits, a scheme allowlist, a path-traversal check and destination approval. No commands are ever run.
- **Source:** §17, §17.3
- **Status:** `documented`

### ADV05 — Disk budget and removable-drive recovery
- **Outcome:** A full disk or an unplugged drive does not lose progress.
- **Priority:** P0 basic · B1. P1 advanced · B4.
- **Depends on:** COR-07
- **Acceptance:** ENOSPC stops the job (`DISK_FULL`), keeps the partial file and never overwrites another file. The space check accounts for known remaining bytes plus a safety margin. A removed volume adds `volume_missing`. When the same volume returns, recovery is validated against volume identity and the partial file.
- **Source:** §7, §17, §17.4
- **Status:** `documented`

### ADV06 — Resume manifest, cancellation guard and completion journal
- **Outcome:** A changed file or a late worker event can never produce a false success.
- **Priority:** P0 · B1
- **Depends on:** ARCH-05, COR-02
- **Acceptance:** The resume manifest stores job and attempt ID, backend build, validator, encoding, expected length/hash, volume and a checkpoint reference. Events from stale attempts are rejected. The journal runs in this order: intent → verify → origin marking/scan → same-volume final placement → complete. A cross-volume move is never called atomic. Crash and changed-resource fixtures show no silent corruption.
- **Source:** §17, §17.4
- **Status:** `documented`

### ADV07 — Local diagnostic centre and support bundle
- **Outcome:** Users can find out why something failed.
- **Priority:** P1 · B4
- **Depends on:** CORE-11, E05
- **Acceptance:** Each problem shows a readable explanation, a stable kind and a next action. The bundle contains versions, OS and browser, a capability summary and a sanitized event log. It excludes secrets, file content and full username or path. The user previews it first, and nothing is uploaded automatically.
- **Source:** §17, §17.6
- **Status:** `documented`

### ADV08 — Scoped integration and plugin system
- **Outcome:** Site adapters can be added without changing the core.
- **Priority:** P2 · B5 (declarative adapters), B6 (runtime plugins)
- **Depends on:** E01
- **Acceptance:** Declarative adapters first. Runtime plugins only behind an explicit capability model: approved origins, temporary folder, size, time, memory and CPU budgets, and a versioned host API. A disabled plugin cannot run. Wasmtime/WASI is evaluated in a spike.
- **Source:** §17, §17.7
- **Status:** `proposed`

### ADV09 — Signed updates, release channels, SBOM and provenance
- **Outcome:** Users can trust updates and see dependencies.
- **Priority:** P0 · B3 (signature verification). P1 · B4 (channels, SBOM, provenance).
- **Depends on:** REL-01
- **Acceptance:** A tampered artifact is rejected. The service checkpoints and migrates before an update. A failed migration still allows a recoverable startup. There is no downgrade without a verified backup. Stable and beta channels are opt-in. A CycloneDX SBOM and SLSA provenance are produced.
- **Source:** §6 (10), §10, §17, §17.9
- **Status:** `documented`

### ADV10 — Paired local-network companion
- **Outcome:** Users can send links from a phone and watch the queue.
- **Priority:** P2 · B6
- **Depends on:** ARCH-06
- **Acceptance:** Disabled by default. Pairing is approved on the desktop and is short-lived. TLS uses key pinning. Access is per device, revocable, and split into view, add and control. An unauthenticated peer cannot control jobs. The native API is never exposed to the network directly.
- **Source:** §14.3, §17, §17.9
- **Status:** `deferred`

### ADV11 — Portable mode and integration repair
- **Outcome:** The app can run portably and recovers when it is moved.
- **Priority:** P1 · B4
- **Depends on:** BRW-07
- **Acceptance:** Relative data layout. Credentials are never exported implicitly. A missing host after a move offers repair or browser fallback. Existing downloads stay intact. Unregistering removes only the app's own entries.
- **Source:** §17, §17.9
- **Status:** `documented`

### ADV12 — Responsive, accessible UI for large queues
- **Outcome:** Keyboard and screen-reader users, and users with very large histories, can work efficiently.
- **Priority:** P0 basic · B2. P1 scale · B4.
- **Depends on:** UI-03
- **Acceptance:** The essential workflow works keyboard-only (add, pause, resume, cancel, reorder, open folder). Focus is visible. Buttons are labelled. Progress announcements are throttled. The list is virtualized for at least 10k items and stays responsive. Bangla and RTL filenames remain identifiable. Formal WCAG conformance is claimed only after an audit.
- **Source:** §17, §17.9
- **Status:** `in-progress`

## Non-goals (current plan)

- DRM circumvention or downloading DRM-protected content (§9, §17.8).
- Promising "every website's video", universal authenticated/POST capture, or zero AV/SmartScreen warnings (§9, §14.4, §16.2).
- Central download proxy, mandatory cloud account, paid tier for core, scheduler, extension or planned media (§10, §15.7).
- Scheduler running while the computer is off or asleep (§5).
- Speed or memory superiority claims without REL-04 evidence (§11).
