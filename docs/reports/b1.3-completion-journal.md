## Finalization behaviour (backend `http`)

| Situation | Outcome |
|---|---|
| Transfer complete, no trusted checksum | intent → verified (SHA-256 computed) → placed (hard link, never over an existing file) → `completed`, `verification.source = local_hash`; staging name removed |
| Trusted `expected_sha256` matches | Same, `verification.source = publisher_checksum` |
| Trusted checksum or known length does not match | `failed`, `CHECKSUM_MISMATCH` (or `INVALID_RANGE`); nothing placed; the bad staging file deleted |
| A file appears at the destination before placement (even concurrently) | `failed`: "a file already exists at the destination; Downova did not overwrite it"; that file untouched; the verified bytes stay as `.downova-part` |
| Crash after `intent` / `verified` / link / `placed` / `complete` | Restart reconciles the journal first and ends `completed` with the exact file; the file is not downloaded again |
| Staging file modified while down (after `verified`) | `failed` ("changed before it was placed"); nothing placed; file left as found |
| Final file modified while down (after `placed`) | `failed`; the modified file is left as found |
| Final file removed while down (after `placed`), staging intact | Placed again from the staging file; `completed` |
| Journal write fails | Nothing verified or moved; retried at the next poll |
| Cancel while finalization holds the job | Waits for it; refused once the file is placed or completed, so a cancelled job never has a placed file |
| aria2 backend | Engine places `<name>` itself; verification in place after placement (a mismatch fails the job, the file stays) |

## Limitations and unverified cases

- **Process kills only; no power-loss claim.** Windows has no directory sync after placement.
- The copy fallback (no hard links: FAT/exFAT, some network shares) is implemented and reasoned about, but **not
  exercised** by a test: every local and CI file system supports hard links.
- A crash in the middle of a copy fallback leaves a partial final file that recovery reports as a collision (explicit,
  never adopted). It is not cleaned up automatically.
- aria2 places before verifying (documented). Its in-place verification is covered only by the existing aria2 process
  tests, not by crash tests.
- Hashing runs under the coordinator lock, so very large files delay other API calls during finalization.
- Origin marking (MOTW) and scanning are not implemented. The UI does not show the verification source yet (B2).

## Reproduction

1. Debug build, Windows/macOS/Linux:

   ```bash
   cargo build -p dm-service -p dm-cli
   ```

2. Start a service that crashes right after placing a finished file:

   ```bash
   DOWNOVA_FAULT=after_place DOWNOVA_CHECKPOINT_TRACE=/tmp/dv/trace.jsonl target/debug/dm-service --data-dir /tmp/dv --download-dir /tmp/dv-dl
   ```

3. Add any HTTP(S) link with a strong ETag (`target/debug/dm --data-dir /tmp/dv add <URL>`). The service aborts once
   the file is placed. `/tmp/dv-dl` holds both `<name>` and `<name>.downova-part`, and the trace shows
   `finalize_placed`.
4. Start it again without `DOWNOVA_FAULT`. The trace shows `journal_reconcile` then `finalized`. `dm list` shows the job
   `completed`, `<name>.downova-part` is gone, and the file's SHA-256 matches the source.
5. Variations:
   - `DOWNOVA_FAULT=hold_before_place`: create `<name>` yourself, then create `/tmp/dv/trace.jsonl.release`. The job
     fails and your file is untouched.
   - A trusted checksum can be given only through the API (`expected_sha256` in `downloads.v1.add`); `dm add` does not
     expose it yet. Process test F03 shows the mismatch case.
