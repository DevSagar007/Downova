## Status presentation (UI-03)

- **Status cell:** a Lucide icon plus the status text, with a tone from the `--color-status-*` tokens.

  | Status | Icon | Tone |
  |---|---|---|
  | Complete | `CircleCheck` | success |
  | Error | `CircleX` | danger |
  | Cancelled | `Ban` | neutral |
  | Paused (manual) | `CirclePause` | neutral |
  | Waiting (policy blocker) | `Hourglass` | warning |
  | Queued | `Clock` | neutral |
  | Connecting | `PlugZap` | info |
  | Downloading | `ArrowDownToLine` | info |
  | Verifying | `ShieldCheck` | info |
  | Scanning | `ScanSearch` | info |
  | Finishing | `FileCheck` | info |

  Manual pause outranks blockers. Colour is never the only cue.
- **Progress bar:** a native `<progress>` with value 0–1000 computed with BigInt from the decimal-string byte counts,
  so it is exact beyond 2^53. A count above the total shows as full.
  - Its accessible name is "Progress of {name}" and its `aria-valuetext` the percent.
  - It is shown only while the download is unfinished with a known, non-zero total; there is no bar and no percent for
    unknown or zero totals.
  - All bytes received still reads "Downloading 100.0%" / "Verifying" / "Finishing" until the service reports
    Complete.
  - Paused and waiting rows use the paused fill.
  - New token `--progress-height`; the width transition follows `--duration-normal` (0 with reduced motion).
- **Announcements:** a polite live region in the status bar announces only completion, failure, cancellation and
  removal, never per-poll progress (design.md §10). The transitions are detected in the provider's list callback.
- **Not invented:** speed, ETA and last try stay "—"; no scan result is shown that the service did not report.

## Cancel download (CORE-03)

- **UI:**
  - File → "Cancel download…" opens a confirmation that names the file and says the download cannot be resumed and
    that **nothing is deleted** (the partial `.downova-part` file stays; `backend.remove` deletes nothing).
  - "Keep downloading" sends nothing. Confirm sends one request; repeated clicks are ignored while pending.
  - The row shows Cancelled only after the service acknowledges.
  - Not offered for failed, finishing (placing), completed or cancelled jobs. The service refusal for a placed job is
    shown with the error catalogue.
- **Service fix:** `Core::cancel` took the attempt out of the job *before* asking the engine to stop. A failed stop
  then lost ownership of a transfer that might still be running. Ownership now ends only after `backend.remove`
  succeeds; a failure is reported and the job keeps its attempt.
  - Test: `a_failed_stop_keeps_ownership_and_reports_the_error`. It fails on the old code. It also checks that late
    progress for the old attempt cannot revive the cancelled job.
- **Distinct actions:** Cancel is separate from Stop (pause), Remove from list and Delete.

## Remove from list (CORE-10, COR-09, ADR 0013)

- **Contract:**
  - `downloads.v1.remove(JobRef)` and an optional `DownloadSnapshot.removed` (schema, Rust, generated TypeScript);
  - examples: remove request, removed snapshot, an invalid non-boolean `removed`.
- **Storage (migration 5):**
  - `jobs.removed_at_ms`, set only by `Store::remove_job`, in one transaction. Completed, failed or cancelled jobs
    with no journal entry only; otherwise `NotRemovable`. The first timestamp is kept.
  - Rows and idempotency records are kept: no `ON DELETE CASCADE` fires.
  - `purge_removed` deletes tombstones older than the key retention only once no key references them.
- **Service:**
  - `Core::remove` refuses unfinished jobs, including paused, blocked, transferring and finalizing ones;
  - it persists before acknowledging; a store failure gives `INTERNAL` + `retry` and changes nothing;
  - lists omit removed jobs, and `get` and replays still answer;
  - startup prunes keys, then tombstones;
  - no file is touched.
- **Shell:** `downloads_remove` (validated job ID), declared in the manifest and granted by name.
- **UI:**
  - File → "Remove from list…" with a confirmation that states that the file and any partial data stay;
  - after success, the next row (or the previous one) is selected and focused and the removal is announced;
  - the acknowledged removal drops the row at once, and older list answers cannot restore it;
  - Delete stays unavailable, and its reason now points to Remove from list, which keeps the file.

## Limitations

- **OS coverage (updated 2026-10-27):** committed as `12966a7`. CI #30 is green on all 4 runners, including windows-latest, where R01 with the B2.2 barrier ran and passed for the first time. Package smoke #20 is green on all 3 OSes, so steps G, H and I passed on macOS and Linux too (job conclusions; per-step logs need authentication).
- **Cancel** leaves the `.downova-part` file in the download folder. Downova never deletes files, and there is no
  "delete partial data" action yet.
- **CORE-10:** no history search, bulk "Clear list", undo or user-set retention. Tombstones are kept for at least the
  30-day key retention.
- **No CLI command** for remove yet (`dm remove`); the API is available to it.
- **Announcements** cover state changes the window observes while polling (at about 1 s), not events.
- **Contrast audit** (UI-02) not done; the status tones use existing tokens.
