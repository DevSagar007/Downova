## 2. What users can do

**Signed-in download (part 1):**
- In a normal Chrome or Edge window, right-click an **https** link and choose **“Download with Downova using my
  sign-in (this time only)”** or **“… and remember it”**.
- The link must have the **same origin** as the page it is on, and it must not be inside a frame of another site.
- The browser asks once for the `cookies` permission for that one site.
- The cookies for that link come from the tab's own cookie store (no partitioned or expired ones) and are sent once.
- Downova downloads it with the native HTTP engine (GET only), sending only the cookies that apply to each
  request. Any hop, retry, resume or segment outside the origin, or from https to http, stops instead.

**Reconnect (part 2):**
- A signed-in download no longer fails when its sign-in goes away. That happens when:
  - Downova restarts (a "this time only" sign-in lives in memory);
  - the site rejects the session (401);
  - the user forgets the sign-in;
  - the credential store is locked.
- Instead it **waits** (`sign_in_required`, “Waiting: sign-in needed”) with its saved part, and nothing is
  downloaded without the sign-in. The desktop and `dm get` explain how to continue.
- On the site, in the same browser profile, right-click the page and choose **“Reconnect a Downova download with my
  sign-in”**. A page lists that site's waiting downloads for this profile, with nothing preselected.
- Choose one, then **Reconnect** (a pause and a stopped queue stay as they are) or **Reconnect and resume**.
- The same download continues from its saved part. The engine re-verifies that part and the file's identity; a file
  that changed on the server is downloaded again whole, never mixed.
- A failed download (from before this change) only gets its sign-in back; Retry starts it again.

**Not supported (refused with a reason, or left in the browser):**
- http;
- another origin, or another browser or profile;
- private windows and third-party frames;
- an ambiguous cookie store;
- no applicable cookie;
- POST, blob: and data: links;
- Firefox, aria2 and proxies;
- a download whose link could not be kept (no data key).

Compatibility with any particular site is not claimed.

## 3. What changed in part 2

- **Holds instead of failures:** admission, startup recovery, an engine `AUTH_REQUIRED` and Forget all hold the
  job. The checkpoint is committed, the attempt released and the partial kept, and the job shows the durable bytes.
  The context becomes `expired` (memory and row) on a 401; expired rows load without their secret.
- **Reconnect:**
  - `downloads.v1.reconnect` and `credentials.v1.reconnectable`;
  - native-host ops `reconnect` and `reconnect_candidates` (validated in the host, `candidates` in the response);
  - `Blocker::SignInRequired`;
  - migration **14**, which rebuilds `operations` to accept `reconnect`, keeping every row;
  - a vault-first, re-check-under-lock, one-transaction commit (`Store::reconnect_job`) with rollback of the store
    entry, and retirement of the old context only when unreferenced.
- **Gap fixes found by the audit:**
  - **cookie-less resume after a restart:** the restored transfer had no session;
  - **Forget left a usable session** inside the paused engine transfer;
  - **a repeated `add_authenticated` replaced the accepted job's sign-in,** including its remembered store entry;
  - **a held job showed undurable bytes;**
  - **the signed-in source display showed the last path segment,** which can be a token. It is now the origin only;
  - the stored-row binding of a held checkpoint was missing, which dropped it at the next start (found by a test);
  - Retry now restarts an auth failure once a sign-in is available.
- **Extension:**
  - the page rule (`checkPage`) refuses third-party frames (`rejected_signin_partitioned`), for links and reconnects;
  - a page context-menu item and `reconnect.html` (explicit radio choice, Reconnect / Reconnect and resume, one
    request per click burst, live update from `storage.session`);
  - `Reconnects` (one operation id per request and download, reused by retries; nothing secret stored);
  - host-cookie selection for a reconnect;
  - English and Bangla.
- **Desktop:** the held state, “sign-in needed”, and reconnect instructions in English and Bangla; error actions
  name the reconnect path.
- **CLI:** the sign-in hint names the browser reconnect; `dm` never accepts a secret.
- **aria2 audit:** a signed public link paused mid-transfer and stopped leaves no file holding its signature. The
  adapter uses no session or log file, and the control file carries no URI. aria2 still refuses sessions.

## 4. Defects found by the new tests and fixed

- The repeated signed-in add overwrote the remembered entry (the service test asserts the entry is unchanged).
- A held job lost its checkpoint at the second restart (the row was not bound to the checkpoint's attempt).
- Reconnecting a failed job that still had an attempt turned it into `queued`; it now stays failed for Retry.
- The extension's e2e hook did not await `signedIn`, so the harness could read the previous hand-off record (S1
  failed in the first Chrome run of part 2); the path now returns its promise.
- A shell-quoting slip removed a backslash from the host-cookie regex; the unit test caught it.

## 7. Limitations (stated, not hidden)

- **Platforms:** everything above ran on Windows only. The macOS Keychain and Linux Secret Service adapters were
  not compiled or run, and real Chrome and Edge ran on Windows only.
- **Partial data without a durable checkpoint** is not resumable (the existing disk-hold rule): such bytes are
  removed when the job is held.
- **A changed resource** restarts cleanly with the new representation (COR-02). The old part is not kept for a
  manual choice.
- **A lost link** (no data key when it was added) cannot be continued by a new sign-in. The user starts again from
  the browser, and the partial stays until the download is removed. Refresh link still refuses signed-in downloads.
- **Parent-domain cookies limited to a deeper path** are not offered by the reconnect read. The reconnect is then
  refused, not broken.
- **File names:** a site that puts a token in the last path segment and sends no file name gives the file that
  name, in the list and on disk.
- **No secure deletion** is claimed for old WAL or free pages, or for backups made outside Downova.
- **Shared contexts** do not occur today (one context per download). The retirement rule only guards the case.
