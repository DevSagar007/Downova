## 2. What users can do

**The supported subset, exactly:**

- In a **normal** Chrome or Edge window, right-click an **https** link and choose **“Download with Downova using my
  sign-in (this time only)”** or **“… and remember it”**.
- The link must have the **same origin** (scheme, host and port) as the page or frame it was clicked in.
- The browser asks once for the optional `cookies` permission and **that one origin**. The extension reads that
  link's cookies from **the tab's own cookie store** at that moment (`chrome.cookies.getAll` for the link and store),
  without partitioned (CHIPS) or expired cookies, and sends them once to Downova.
- Downova downloads it with the **native HTTP engine** (GET only), sending only the cookies that apply to each
  request (RFC 6265 domain, path, Secure, expiry). A redirect, retry, resume or segment that leaves the origin, or
  goes from https to http, stops with “led to another site or to an insecure link”; credentials are never sent there.
- **Temporary** (default): the sign-in lives in the service's memory until its downloads finish, or the service
  stops. **Remembered** (explicit choice): it is also kept in the OS credential store, survives restarts, and is
  removed by **Forget sign-in** (desktop details, `dm credentials-forget`), which pauses the downloads using it.
- The desktop details and `dm get` / `dm credentials` show the site, browser, mode and state (available, missing,
  locked, unavailable, expired, forgotten) with what to do; never a cookie or token.

**Not supported (stays in the browser or is refused, with a reason):** http links; a link of another origin than
its page; private windows; an ambiguous cookie store; no usable cookie; POST, blob:, data:; Firefox; aria2
(`BACKEND_CAPABILITY_UNAVAILABLE`); proxies. Compatibility with any particular site is **not** claimed: sites that
bind sessions to the browser (fingerprints, client hints, TLS channel binding, single-use links) may refuse it, and
then the download stops with “the website no longer accepts this sign-in”.

## 3. What changed

- **ADR 0027** (secret classes, temporary vs remembered, credential identity and scope, vault error mapping,
  SQLite/vault consistency, URL and checkpoint sealing, cookie selection and redirect rules, revocation, expiry and
  reauthorization).
- **SEC-02 (`dm-platform::vault`):** store/resolve/replace/delete over keyring-core stores (Windows Credential
  Manager, macOS Keychain, Linux Secret Service), namespace `Downova/<sha256(data folder)[:12]>`, 2,560-byte bound,
  `Locked`, `Missing`, `Unavailable`, `TooLarge`; calls run on blocking threads, never under the coordinator lock.
  Debug builds only: `DOWNOVA_VAULT=memory|off|file` for tests.
- **SEC-01 (storage):** migration 13 (`credentials`, `jobs.credential_id`, `jobs.url_sealed`,
  `resume_checkpoints.sealed`). AES-256-GCM (`ring`) with a data key from the vault; the plain URL column holds a
  display form; without the key protected parts are not persisted. Legacy plaintext rows are re-sealed one row per
  transaction, then a WAL checkpoint and VACUUM. An update while the key is unreadable keeps the sealed link.
- **Service:** `downloads.v1.add_authenticated`, `credentials.v1.list`, `credentials.v1.forget`; pending row →
  vault → job → active, with cleanup on failure and startup reconciliation; restart restores remembered sign-ins and
  marks temporary ones missing; a locked store holds jobs with “unlock and restart” without losing the sealed link;
  a site rejecting the session shows `expired`; diagnostics gain a counts-only `secrets` section.
- **Engine:** `TransferRequest.session`; the per-request `Cookie` header; scope checks before the first request,
  every redirect hop, resume and segment; replace-source refuses sessions; aria2 reports `authenticated_get`
  unsupported and refuses sessions.
- **Contracts:** the error kinds `AUTH_SCOPE_UNSUPPORTED` and `CREDENTIAL_STORE_UNAVAILABLE`; capability
  `authenticated_get`; `AuthInfo`, `CookieInput` (ingress only, `SecretTransit` with a redacted Debug),
  `SessionInput` (validated bounds: ≤ 64 cookies, ≤ 16 KiB), the credential types, the native-host
  `add_authenticated` op; examples and invalid examples; TypeScript regenerated.
- **Native host:** `add_authenticated` checks https, origin equality, bounds and the idempotency key before
  forwarding; a locked store maps to `unavailable`.
- **Extension:** two context-menu items for https links; `signin.ts` (scope, store, cookie selection);
  `cookies` added to `optional_permissions` only; records keep origin, store id, browser and remember choice, never
  cookies; cookies are re-read on retry; popup line and refusal reasons in English and Bangla.
- **CLI:** `dm credentials`, `dm credentials-forget <ID>`, a “Sign-in” line in `dm get`.
- **Desktop:** the sign-in note in the details with Forget (one request per click burst, keyed per job), Tauri
  commands `credentials_list` and `credentials_forget` (metadata only), English and Bangla strings; the sign-in error
  action now names the browser path instead of “cannot sign in yet”.
- **Test-only:** `DOWNOVA_TEST_CA_DER` (debug builds only) lets process tests reach an HTTPS fixture.

## 4. Defects found and fixed during the batch

- **A token in a path segment leaked into `source_display`** for signed-in jobs (found by the synthetic-secret
  test): signed-in jobs now show `origin/…/last-segment` only.
- **A locked credential store at startup would have erased sealed links:** the job was failed and re-written
  without the sealed copy. Now the failure is held in memory only and the storage update keeps an existing sealed
  link for an unchanged URL; the next start after an unlock continues (unit and storage tests).
- **A race ended a temporary sign-in before its job existed** (found by the real native-host end-to-end test): the
  poll loop's sweep ran while the job was still being added. Contexts being added are now exempt.
- **Baseline:** the B3.2 acceptance script was not Prettier-formatted (the one failing verify group at `b701e3c`).
