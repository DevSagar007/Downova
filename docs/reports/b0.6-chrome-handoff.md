## Supported category

Only an explicit **context-menu hand-off of a public `http`/`https` GET link**. Everything else stays with the browser,
and nothing is taken from it:

| Category (research §15.5) | B0.6 behaviour |
|---|---|
| Public GET link, context menu | Handed off: extension → host → `downloads.v1.add` |
| Link with embedded credentials (`user:pw@`) | Refused by both the extension and the host |
| `ftp:`, `file:`, `data:`, `blob:`, `javascript:` and other schemes | No menu item (`targetUrlPatterns`); refused if forced |
| Authenticated links (cookies or session) | Not detectable here. The service reports `AUTH_REQUIRED` or `LINK_REFRESH_REQUIRED`; no cookies are sent (BRW-05) |
| Browser downloads (automatic capture), POST, single-use | Not touched. No `downloads` permission, nothing intercepted, cancelled or erased (BRW-04, B2) |

## What was built

| Piece | Implementation |
|---|---|
| Contract | `NativeHostRequest` (`hello` and `add` only; closed, `additionalProperties: false`), `NativeHostOutcome`, `NativeHostResponse` in `service-api.v1.schema.json`. TypeScript is generated, the Rust mirror is in `dm-domain::api`, and there are examples for an arbitrary-RPC request, an `ftp:` link and an extra-field request |
| Host `dm-browser-host` | 4-byte native-endian framing with exact reads; 64 KiB request cap checked before allocation; 1 MiB response cap. Exact origin allowlist (argv origin). Only `add` is forwarded, as `downloads.v1.add` with profile `downloads`. stdout carries frames only; stderr never carries URLs |
| Service start policy | The host **never starts** the service. With no service it answers `unavailable` ("open the Downova app, then try again"). Reason: on Windows a child inherits the browser's pipe handles and job object, and preventing that needs unsafe code. Browser or host exit cannot stop the service, because the host neither owns nor starts it |
| Outcomes | `accepted` (job returned; the transfer has not necessarily started). `rejected`. `unavailable` (nothing sent). `uncertain` (sent, but no acknowledgement within 10 s, or the connection was lost); retry with the same key |
| Idempotency | The same key returns the same job, and a different payload with the same key returns `IDEMPOTENCY_CONFLICT`, while the service keeps running. Restart-safe idempotency is B1 |
| Registration | `dm-browser-host register` / `repair` / `unregister` / `status`, per user, for Chrome stable/beta/dev/canary, Chromium and Edge. Windows: manifest under `%LOCALAPPDATA%\Downova\native-messaging\<browser>\` plus an `HKCU\Software\…\NativeMessagingHosts\com.downova.host` key. macOS and Linux: the browser's per-user `NativeMessagingHosts` folder (no Canary on Linux). It refuses relative paths and AppImage mounts (`/.mount_`, `$APPDIR`). Unregister removes only our key and our manifest. `--root` and `--registry-root` allow isolated tests |
| Extension `apps/extension` | MV3, TypeScript, built with Vite. Permissions: `contextMenus`, `nativeMessaging`, `storage` only, with no host permissions, content scripts or cookies. The development ID `bkmpnfclpdmcbdgmeakmnoilmkdmdppf` comes from the manifest `key` (public key only). Each action gets a new `ext_…` key, stored in `chrome.storage.local` *before* sending. A stopped worker leaves a `sending` record that becomes `uncertain` after 35 s. A 30 s timeout gives `uncertain`. Retry reuses the key with a new `request_id` |
| Status surface | Toolbar popup: an `aria-live` list with text states ("Accepted by Downova", "Not accepted", "Downova unavailable", "Not confirmed"), the job ID, the reason, and Retry/Dismiss buttons with accessible names. Retry appears only for `uncertain` and `unavailable`. The badge is a secondary cue |
| Packaging | `dm-browser-host` is built by `scripts/package.mjs` and bundled as a Tauri `externalBin` next to `dm-service`. The installer does not register it yet |

## Not done or limited

- No real Chrome/Edge run on any OS, so BRW-01 is not `verified`.
- Idempotency survives only while the service runs (B1).
- The host never starts the service. Without a running service the result is `unavailable` until the user opens Downova
  (login autostart, ARCH-01).
- Only the development extension ID is allowed. The store ID and Firefox (`allowed_extensions`) come later.
- The installer does not register the host, and uninstall does not unregister it (REL-01).
- The extension UI is English only.
