## Supported category

Only an explicit **context-menu hand-off of a public `http`/`https` GET link**. Nothing is taken from the browser:

| Category (research §15.5) | B0.6 behaviour |
|---|---|
| Public GET link, context menu | Handed off: extension → Chrome native messaging → host → `downloads.v1.add` |
| Link with embedded credentials (`user:pw@`) | Refused by the extension and by the host |
| `ftp:`, `file:`, `data:`, `blob:`, `javascript:` and other schemes | No menu item (`targetUrlPatterns` http/https); refused if forced |
| Authenticated links (cookies or session) | Not detectable here. No cookies are sent, and the service reports `AUTH_REQUIRED` or `LINK_REFRESH_REQUIRED` (BRW-05) |
| Browser downloads, automatic capture, POST, single-use | Not touched. No `downloads` permission, so nothing is intercepted, cancelled or erased (BRW-04, B2) |
| Incognito | `"incognito": "not_allowed"` |

## What was built

| Piece | Implementation |
|---|---|
| Contract | `NativeHostRequest` (`hello`, `add`; closed), `NativeHostOutcome` and `NativeHostResponse`, with valid and invalid examples. TypeScript is generated, and the Rust mirror is in `dm-domain::api` |
| Host `dm-browser-host` | 4-byte native-endian framing with exact reads; 64 KiB request cap checked before allocation; 1 MiB response cap. Exact origin allowlist (the origin from argv). Only `add` → `downloads.v1.add` (profile `downloads`) and `hello`. stdout carries frames only; stderr never carries URLs |
| Service policy | The host **never starts** the service. When none is running it returns `unavailable` with "the Downova download service is not running; open the Downova app, then try again". On Windows a child of the host would inherit the browser's pipe handles and job object. Browser or host exit cannot stop the service |
| Outcomes | `service_ready` (hello), `accepted` (job returned; the transfer has not necessarily started), `rejected`, `unavailable` (nothing sent), `uncertain` (sent, but no acknowledgement in time; retry with the same key) |
| Idempotency | The extension creates one key per explicit action and stores it in `chrome.storage.local` **before** sending. A retry sends the same key and URL with a new `request_id`; a new action gets a new key. The service returns the same job for the same key and `IDEMPOTENCY_CONFLICT` for a different payload, while it keeps running. **Restart-safe idempotency is B1** |
| Worker loss | A record left in `sending` by a stopped worker becomes `uncertain` (retryable) after 35 s. Extension timeouts are 30 s for `add` and 10 s for `hello` |
| Response checks | `v` = 1, `request_id` must match, the outcome must be known, and `accepted` must carry a `job_id`. Anything else is `uncertain`, never a failure or a success. A missing or forbidden host is `unavailable` ("install or repair") |
| Privacy | The popup and its accessible names show scheme, host and path only: the query becomes `?…`, and the fragment and credentials are dropped. The extension logs nothing; the host logs only request IDs and outcomes |
| Status surface | The popup has a **Service** line (role `status`): "Service ready / unavailable / status unknown" plus the reason and a "Check again" button. It also has an `aria-live` hand-off list with text states, job ID, reason, Retry (only for `uncertain` and `unavailable`) and Dismiss, plus "Clear list". At most 20 records are kept, and settled records are dropped after 7 days |
| Identity | The manifest `key` holds a public key only. Its SHA-256 yields `bkmpnfclpdmcbdgmeakmnoilmkdmdppf`, which is checked by `manifest.test.ts` and by the real Chrome run. The host allowlist is exactly `chrome-extension://bkmpnfclpdmcbdgmeakmnoilmkdmdppf/`; there are no wildcards |
| Registration | `register` / `repair` / `unregister` / `status`, per user. Supported: Chrome stable, beta, dev and canary; Chromium; Edge. Windows uses the HKCU key plus a manifest under `%LOCALAPPDATA%\Downova\native-messaging`; macOS and Linux use the browser's `NativeMessagingHosts` folder. Relative paths and AppImage mounts are refused, and only Downova's entries are removed |
| Packaging | `scripts/package.mjs` builds and stages `dm-browser-host` as a Tauri `externalBin` beside `dm-service` and `dm`. **Installer registration is deferred** (REL-01): today the user runs `dm-browser-host register` |
| Real-browser test | `scripts/e2e/chrome-handoff.mjs`: an isolated temporary profile, `--remote-debugging-pipe` and `Extensions.loadUnpacked`. Registration is reversible: on Windows the HKCU key is restored afterwards; on macOS and Linux the manifest goes in the profile's own `NativeMessagingHosts`. It also uses an isolated service and downloads. It runs in CI on windows-latest, macos-latest and ubuntu-24.04 (added in this change, not yet run there) |

### Real-browser steps (Chrome 155.0.8059.85, Windows 11, headless=new, isolated profile)

| Step | Result |
|---|---|
| 1 Unpacked extension loads; the ID Chrome reports equals the host allowlist | passed (`bkmpnfclpdmcbdgmeakmnoilmkdmdppf`) |
| 2 The popup readiness check (popup → worker → `sendNativeMessage` → host → service) | passed: "Service ready. Downova 0.1.0 is running (backend http)." |
| 3 Context-menu hand-off → accepted → 3 MiB fixture completed, SHA-256 matches | passed |
| 3b The popup shows "Accepted by Downova … has not necessarily started" | passed |
| 4 Lost acknowledgement (1 ms timeout) → `uncertain`. Chrome closed and restarted, giving a new worker with the same profile; the record is still `uncertain` with the same key. Retry → `accepted`. The service holds **one** job for the link | passed |
| 5 Chrome closed at 1 MiB of 6 MiB of a throttled transfer: no host process left, the service is alive, the transfer completes, SHA-256 matches | passed |
| Registration removed afterwards; other hosts' keys untouched (IDM, FDM, Claude, BrowserCore) | passed |

The context-menu **click** itself is simulated. Chrome cannot click its native menu from automation, so step 3 calls the
worker's registered `contextMenus.onClicked` listener with the same `{menuItemId, linkUrl}` a click delivers. The hook
exists only in the `vite build --mode e2e` bundle, not in `dist/`. Everything after the click is the real browser path.

Runs: step 5 initially closed Chrome before any bytes moved, so it was tightened to wait for bytes in flight. The
tightened script then passed 3 consecutive runs.

## Not done or limited

- BRW-01 is not `verified`: real Chrome has passed on Windows only. Edge, macOS and Linux have not run in a real
  browser, and nobody has clicked the menu by hand.
- Idempotency holds only while the service runs (B1). A lost acknowledgement followed by a service restart could create
  a second job.
- The host requires a running service; there is no login autostart yet (ARCH-01).
- Only the development extension ID is allowed. Store IDs and Firefox (`allowed_extensions`) come later.
- The installer neither registers nor unregisters the host (REL-01). The extension UI is English only.
- The CI ubuntu-22.04 failure on `330d306` was not read and its fix is unconfirmed.
