## What changed

- **`dm remove <JOB-ID>`** calls `downloads.v1.remove`.
  - Human output adds "Removed yes: not in the list; the file was kept".
  - JSON is the snapshot with `removed: true`.
  - Unfinished jobs are refused by the service with exit 4.
- **`dm shutdown [--pause-downloads]`** calls `service.v1.shutdown` with `{}` or `{"mode": "pause_downloads"}`.
  - The acknowledgement is not reported as termination: the CLI then waits until the service's endpoint stops
    answering. The bound is `RunOptions::stop_timeout`, 20 s by default.
  - Exit 0 and `{mode, paused_jobs, stopped: true}` only when the service is gone.
  - If it is still running, exit 1 with "acknowledged the stop (N paused) but was still running after 20 s".
  - `--pause-downloads` is refused for every other command.
- **Help and usage text** list both commands. JSON shapes and exit codes of existing commands are unchanged.

## Browser extension part of the B2.3 plan

The plan asked for a popup that shows whether the service is reachable and links to the app. The popup has done the
first part since B0.6:
- "Check again" sends `hello` through the native host;
- the states are "Service ready / unavailable / status unknown" with detail. When the service is not running it says
  "the Downova download service is not running; open the Downova app, then try again";
- tests: `interpretHello` and `renderService`.

**Nothing new was added.** A link that *opens* the desktop app is not possible within the current permissions:
- extensions cannot launch local programs;
- a custom URL scheme would need installer registration (REL-01);
- the native host deliberately never starts the service (B0.6: browser job objects and pipe handles).

This is recorded as a gap, not implemented.

## Limitations

- **F01 stays `in-progress`:** the desktop and the CLI generate different idempotency keys, so adding the same link
  from both creates two jobs. Reboot behaviour is not documented yet.
- **`dm shutdown` without `--pause-downloads`** keeps the downloads' intent: they continue after the next start.
- **Extension:** no "open the app" link (see above).
- **OS coverage:** committed as `10ae139`;
  [CI #31](https://github.com/DevSagar007/Downova/actions/runs/40471760829) passed on all 4 runners and
  [package smoke #21](https://github.com/DevSagar007/Downova/actions/runs/40471760744) on all 3 OSes (recorded in
  B2.5).

## Next: B2.5 (bounded) — the B2 exit blocker

B2 exits when install → right-click a link in Chrome or Edge → the file arrives, with the UI showing progress, on
all three OSes. Today the installer does not register the native host (B0.6, REL-01), so a fresh install cannot
hand off. B2.5:
- **Install:** the packaged installers register the native-messaging host for Chrome and Edge per user (Windows
  registry `HKCU` entries; macOS and Linux manifest files under the per-browser directories), with the extension
  origins on the allowlist.
- **Uninstall** removes only Downova's own entries. A `dm-browser-host --repair` mode rewrites them.
- **Packaged smoke:**
  - after install, the host manifest exists and points to the installed host;
  - the existing real-Chrome hand-off test runs against the installed host instead of a test registration;
  - after uninstall, the entries are gone.
- **Out of scope:** Firefox, Edge real-browser automation where unavailable, queues, the scheduler and event
  streaming.
