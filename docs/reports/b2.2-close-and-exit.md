## 1. CI #28 Windows failure (CORE-04 test)

**Observed** (the CI annotation; full logs need authentication). After a kill and restart, `completed_files_are_exact`
found a job `Failed` with `SERVICE_UNAVAILABLE`: "the download was interrupted when the Downova service stopped before
any resumable progress was saved". That is the honest result for a job that had no usable checkpoint when it was
killed.

**Investigation.**
- **Where checkpoints come from.** The old test waited only for a newer committed checkpoint of the single-connection
  job, then killed a service that also ran the segmented job. Every committed checkpoint is traced with its attempt
  (`DOWNOVA_CHECKPOINT_TRACE`).
- **How a job ends up interrupted.** The stored checkpoint of a job is removed whenever its row is saved with a
  different attempt or none (`drop_stale_checkpoint`). That happens when an attempt is discarded for an automatic
  retry. So a job is reported interrupted after a kill in two cases:
  - it never had a committed checkpoint;
  - it was killed after a transient failure, while waiting for the retry.

  Both are correct, documented behaviours (ADR 0007, COR-04).
- **Experiment.** A throwaway variant killed the service 1 ms after the single-connection job's first checkpoint
  event. In 6 of 6 runs the segmented job already had a committed checkpoint and recovered. The CI failure did not
  reproduce locally, either before or after the change.
- **Production code.** No path was found that loses or rejects a committed checkpoint. **No production recovery defect
  is claimed or fixed.** The cause on the CI runner is not proven.

**Repair (test).** R01 now kills only at a bounded, observable barrier (`wait_all_durable`, ≤ 60 s, no fixed sleeps):
- every unfinished job must have a `checkpoint` or `recovered` trace event for the attempt it runs *now*, and the
  single-connection job a newer one than at the previous kill;
- completed jobs are excluded only after their files are verified;
- a job that is `failed` or `cancelled` before a kill fails the test with its checkpoint trace.

Every "no failed job" assertion now prints that job's trace, so a recurrence shows whether a committed checkpoint
existed.

The service also traces `retry_scheduled` when it discards an attempt for a retry, so that case becomes visible. This
is a test hook only, like the other trace events.

The interrupted-before-checkpoint behaviour stays covered by `jobs_and_idempotency_survive_a_service_kill`.

**Runs:**
- R01 alone: PASSED.
- The full `http_backend_process` binary: 5/5 runs PASSED (46 tests, parallel), the same load as CI.
- A Windows CI run is needed to show that the barrier holds there.

## 2. Exit and stop (service, ADR 0012)

- **Contract:**
  - `service.v1.shutdown` takes `ShutdownParams { mode?: keep_state | pause_downloads }` and answers
    `ShutdownResult { mode, paused_jobs }`;
  - schema, Rust mirror and generated TypeScript updated;
  - examples: 3 valid, 2 invalid (unknown mode, extra field).
- **`Core::begin_shutdown`:**
  - sets the stopping flag under the coordinator lock;
  - with `pause_downloads`, pauses each running, non-finalizing job durably: backend pause, checkpoint commit and
    `desired_state = paused` persisted before the acknowledgement.
- **While stopping:**
  - admission starts nothing;
  - new adds and resumes are refused with `SERVICE_UNAVAILABLE`;
  - replays and reads still answer.
- **Ctrl+C** enters the same state with `keep_state` before the existing checkpointing shutdown.
- **RPC:**
  - only a successful dispatch stops the server;
  - params must be a JSON object for every method. Serde had accepted `[]` as `{}`: found by the new test and fixed.
- **Recovery:** a paused job without an attempt (never started, or waiting for a retry) waits again paused instead of
  being reported as interrupted.

## 3. Desktop (UI-04)

- **Shell** (`apps/desktop/src-tauri/src/lifecycle.rs`):
  - `<data>/desktop-settings.json` holds `close_behaviour` (`hide_to_tray` by default, or `close_window`); damage
    falls back to the default;
  - the tray menu has "Open Downova" and "Exit and stop downloads", relabelled from the UI's catalogue;
  - a close request hides the window, or minimizes it when no tray could be created, or closes the UI;
  - single instance: a second launch shows, unminimizes and focuses the existing window and exits;
  - `service_exit_and_stop` refuses a second request while one runs, sends `pause_downloads`, waits ≤ 20 s for the
    endpoint to stop answering, and quits only after that;
  - four new commands (`desktop_settings_get/set`, `tray_set_labels`, `service_exit_and_stop`), each declared in the
    app manifest and granted by name.
- **UI:**
  - `DesktopShell` interface (Tauri and browser implementations) injected through `ServiceProvider`;
  - Options → "When the window is closed", with notes for no tray and for a save failure;
  - `ExitDialog`, the one confirmation for the Tasks menu and the tray: Cancel changes nothing; one request however
    often Confirm is pressed; the result is verified stopped, still running, or not stopped (unreachable, unconfirmed
    or refused, with the error copy);
  - English and Bangla strings.

## Limitations

- **OS coverage (updated 2026-10-27):** committed as `88e550e`. Package smoke #19 is green on all 3 OSes, so steps G and H passed on macOS and Linux (job conclusion). CI #29 is green on macOS and both Ubuntu runners; windows-latest failed on a DNS error fetching a crate before compiling, so R01 has still not run there. Manual tray clicks: not performed. Linux single instance needs a
  D-Bus session; the smoke workflow now runs under `dbus-run-session` and installs `dbus`.
- **Linux tray:** where no StatusNotifier host shows the icon, the tray may be created yet invisible. Hiding then
  leaves the window reachable only by a second launch. This is not detectable from the app.
- **macOS:** closing the window hides it, and the app stays in the Dock and menu bar. Dock-icon reopen is not wired
  (the tray menu and a second launch are).
- **Uncertain exit:** an exit whose acknowledgement is lost may still have paused downloads and be stopping. The
  dialog says so and lets the user check before trying again.
- **ARCH-09:** only the UI-close case is covered. Browser close, native-host disconnect, OS logout, sleep and reboot
  are not.
- **R01 on Windows CI:** the root cause of the #28 failure is not proven (see §1).
