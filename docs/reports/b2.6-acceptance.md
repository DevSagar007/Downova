**Linux diagnosis** (from timing and code; not confirmed from the log):
- 632 s ≈ 2 × 300 s, the time limit for each real-browser child run (Chrome, then Edge), plus about 30 s of
  ordinary steps. Both Linux browser runs most likely **hung** until they were killed.
- The Linux smoke runs under `dbus-run-session` (added in B2.2 for single-instance); the CI browser step does not.

**Classification:** a test-harness defect (browser launch flags and unbounded waits), not a product defect. Product
evidence on Linux for R1–R5 and D0/D2 is therefore **missing**: the steps after R3 still ran, but their rows are not
readable.

### Dedicated download folder

The service takes its download folder from `DOWNOVA_DOWNLOAD_DIR` when the desktop starts it. **Quit Downova
completely first** (Exit and stop downloads), then open it from a terminal:

- **Windows** (PowerShell, NSIS per-user install):

  ```powershell
  $env:DOWNOVA_DOWNLOAD_DIR = "$env:USERPROFILE\Downova-acceptance"; & "$env:LOCALAPPDATA\Downova\dm-desktop.exe"
  ```

- **macOS:**

  ```bash
  DOWNOVA_DOWNLOAD_DIR="$HOME/Downova-acceptance" /Applications/Downova.app/Contents/MacOS/dm-desktop
  ```

- **Linux (.deb):**

  ```bash
  DOWNOVA_DOWNLOAD_DIR="$HOME/Downova-acceptance" dm-desktop
  ```

Check a file's hash with one of:

```powershell
Get-FileHash -Algorithm SHA256 "$env:USERPROFILE\Downova-acceptance\downova-acceptance-a.bin"
```

```bash
shasum -a 256 ~/Downova-acceptance/downova-acceptance-a.bin
```

```bash
sha256sum ~/Downova-acceptance/downova-acceptance-a.bin
```
