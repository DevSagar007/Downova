### Linux failure and confirmed cause

Both Linux browser runs reached "installed service already running" and "product registration for
\<browser\> found and owned by this installation", then failed in the e2e before the extension step. The e2e
result records `Extensions.loadUnpacked: no answer from the browser in 60 s` for both. No job was accepted, so R4
waited 60 s and failed, and D2 looked for a hand-off file that had never been produced. Those two are **downstream**
failures, not evidence that uninstall deleted data.

Cause, confirmed from Chromium source (the job log itself is not publicly readable):

- Chrome 136+ starts the DevTools pipe only when `--user-data-dir` is **not** the default:
  `IsRemoteDebuggingAllowed` rejects `is_default_user_data_dir`
  ([`remote_debugging_server.cc`](https://chromium.googlesource.com/chromium/src/+/main/chrome/browser/devtools/remote_debugging_server.cc)),
  and `chrome::IsUsingDefaultDataDirectory()` compares `DIR_USER_DATA` with `GetDefaultUserDataDirectory()`
  ([`chrome_paths.cc`](https://chromium.googlesource.com/chromium/src/+/main/chrome/common/chrome_paths.cc)).
- On Linux `GetDefaultUserDataDirectory()` is `$CHROME_CONFIG_HOME` (else `$XDG_CONFIG_HOME`, else `~/.config`) plus
  the browser directory
  ([`chrome_paths_linux.cc`](https://chromium.googlesource.com/chromium/src/+/main/chrome/common/chrome_paths_linux.cc)).
  The product writes the manifest into exactly that directory, and the harness launched the browser with the
  manifest's grandparent as `--user-data-dir`, so the two were equal and DevTools never started.
  See the [Chrome 136 change](https://developer.chrome.com/blog/remote-debugging-port).
- macOS's default is the real OS home, not the isolated `HOME`, and Windows product registration uses a temporary
  profile. Both were non-default, so both passed.
- Native messaging is unaffected: the restriction covers DevTools only, and the product uses native messaging. This
  is a test-harness defect, not a product defect.

### Linux repair (committed in `61acd6d`; scripts only)

| Change | Why |
|---|---|
| `scripts/lib/browser-profile.mjs` (+ 3 unit tests) decides whether the profile is the platform default; in Linux product-registration mode the **browser process** gets `XDG_CONFIG_HOME` and `CHROME_CONFIG_HOME` pointing at `<work>/browser-config-home` | Makes the browser's computed default differ from the profile, so Chrome 136+ starts DevTools, while `--user-data-dir` stays on the product directory and the browser still reads the product's manifest there. Nothing is copied, linked or registered by the harness |
| `chrome-handoff.mjs`: `Browser.getVersion` readiness (20 s) before `Extensions.loadUnpacked`; per-call timeouts; distinct "DevTools transport unavailable" and "extension loading failed" errors | Names the failing phase instead of a generic 60 s stall |
| `chrome-handoff.mjs`: bounded (8 KiB), sanitised browser stderr, exit code, signal and timestamps; `browser-stderr.log` and `results.browser_diagnostics` | The browser's own message is the only explanation for a refusal; paths are redacted |
| `chrome-handoff.mjs`: every launched browser is tracked and closed (short bounded `Browser.close`), or killed, in `finally` | A startup failure or a second launch cannot leak a browser process |
| `packaged-smoke.mjs`: R4 is `unavailable` with "not run" when the Chrome hand-off produced no job; failure records include exit, signal and the `e2e.log`/`browser-stderr.log` tails | Downstream steps no longer masquerade as independent failures or hide the reason |
| `packaged-smoke.mjs`: D2 is registration/data only; D2b checks the hand-off file's survival and is `unavailable` when no file was ever produced | Uninstall evidence is separated from the hand-off's evidence |
| `scripts/verify.mjs`: the unit tests run in the `structure` group | The profile decision cannot silently regress |

No assertion was removed or loosened: the SHA-256, one-job, ownership, cleanup and paused-after-restart checks are
unchanged. There are no added retries.

### Dedicated download folder

The service takes its download folder from `DOWNOVA_DOWNLOAD_DIR` when the desktop starts it. **Quit Downova
completely first** (Exit and stop downloads), then open it from a terminal:

- **Windows** (PowerShell, NSIS per-user install):

  ```powershell
  $env:DOWNOVA_DOWNLOAD_DIR = "$env:USERPROFILE\Downova-acceptance"; & "$env:LOCALAPPDATA\Downova\dm-desktop.exe"
  ```

- **macOS:**

  ```bash
  DOWNOVA_DOWNLOAD_DIR="$HOME/Downova-acceptance" /Applications/Downova.app/Contents/MacOS/dm-desktop
  ```

- **Linux (.deb):**

  ```bash
  DOWNOVA_DOWNLOAD_DIR="$HOME/Downova-acceptance" dm-desktop
  ```

Check a file's hash with one of:

```powershell
Get-FileHash -Algorithm SHA256 "$env:USERPROFILE\Downova-acceptance\downova-acceptance-a.bin"
```

```bash
shasum -a 256 ~/Downova-acceptance/downova-acceptance-a.bin
```

```bash
sha256sum ~/Downova-acceptance/downova-acceptance-a.bin
```
