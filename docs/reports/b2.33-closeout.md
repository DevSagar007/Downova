## 1. Installed-app runbook corrected

[b2.32-installed-acceptance-runbook.md](b2.32-installed-acceptance-runbook.md), checked against the code and the ADRs:

- **C4/C5, admission:**
  - **Was:** lowering the global limit to 2 left six running, and then raising it back to 6 was expected to start a
    seventh, although six already held the six slots.
  - **Now:** C4 asserts the non-preemptive decrease alone. C5 raises the global **and** Main limits to 7, so
    capacity exists, and says why 6 would not start it.
- **Exit and stop (C9/C10):**
  - **Was:** "downloads continue" after reopening.
  - **Now:** following ADR 0012 and the service test
    `exit_and_stop_pauses_unfinished_jobs_durably_and_they_stay_paused_after_restart`, every unfinished download is
    paused durably and nothing starts by itself after reopening. The user presses Resume (or runs
    `dm resume <JOB-ID>`), and the download continues from its committed offset (`/__stats` shows the ranged request).
  - The limits persist.
- **Queue stop/start (C7):** stopping a queue is policy, not intent (ADR 0017). Running transfers are checkpointed
  and carry `queue_stopped`, a manual pause stays a pause, and starting the queue never resumes a manually paused
  download.
- **Fallback F1:** the helper **never starts the service** (`handler.rs`, `NOT_RUNNING`), so a stopped service is a
  deterministic "unavailable". The automated counterpart is X4, which runs the real host against an empty data
  folder.
- **Corrected details:**
  - the Windows manifest folder is `%LOCALAPPDATA%\Downova\native-messaging\` (not `…\NativeMessagingHosts`), and
    both HKCU keys are named;
  - `dm-browser-host` needs `--browser chrome --browser edge`, because without it only Chrome is handled;
  - the MSI has no install or uninstall hook, unlike NSIS;
  - the AppImage refuses to register the helper while it runs from its mount, so the browser rows need the `.deb`;
  - `fixture-server.mjs` binds `127.0.0.1` only, so it must run on the machine under test (the earlier "or the LAN"
    was wrong);

- **F3 (lost acknowledgement)** is no longer "not covered": it points to the automated rows X1–X6 (§2), because a

## 2. Timeout and lost-acknowledgement acceptance (X1–X8)

- **Mechanism:**
  - `scripts/e2e/fault-host.mjs` (test only) is a native-messaging host placed in front of the real installed host.
  - `chrome-handoff.mjs` (`--fault-steps`; the packaged smoke passes it) changes only the `path` of the browser's
    Downova manifest, in the run's isolated location, then restores it byte for byte (X7). `allowed_origins` is
    untouched.
  - The mode is read on every launch:
    - `silent`: never answers;
    - `exit-after-accept`: the real host and service accept, then the helper exits without replying;
    - `mismatch`: the real reply is sent under another request id;
    - `unavailable`: the real host runs against an empty data folder;
    - `pass`: forwards normally.
  - Every launch is logged to `fault-host.jsonl`.
- **Rows:**

  | Row | Fault | Asserted |
  |---|---|---|
  | X1 | the helper never answers (4 s acknowledgement timeout) | uncertain, no job; the retry once it answers uses the same key with a new request id → accepted, one job |
  | X2 | the service accepted, the acknowledgement was lost (the helper exited) | uncertain, never accepted; the retry returns **the job the service created first**; one job |
  | X3 | an acceptance under a different request id | uncertain; the same-key retry returns the same job; one job |
  | X4 | no service | a definite `unavailable` (not uncertain); no job |
  | X5 | an unsupported link | `rejected_scheme`, no helper launched |
  | X6 | automatic capture with a non-matching acknowledgement | uncertain; the browser keeps and **completes** its download, never cancelled by Downova; one key over every attempt; one job |

- **Difference from a normal installed build:** a `.cmd`/`sh` wrapper and Node sit in front of the installed host,
  and the extension is the e2e build (the build that exposes the test hooks). The host, the service and the browsers
  are real.
- **Unit regression:** `handoff.test.ts` checks that a lost or mismatched acknowledgement stays uncertain and that
  retries keep the key, against a service model that stores jobs by key. Mutation-checked: when retries send a new
  key, the test fails.
- **X8** (added during the runs): the helper is not installed, because the manifest is missing while its
  registration remains. Asserted: a definite `unavailable` with `host_missing`, no helper started, no job.

## 3. Measurements made trustworthy

- **Before** (the B2.32 `measure.mjs`):
  - an active run stayed `ok` when a download gained no bytes, finished before the window ended, ran under limits
    that were not applied, failed, timed out or had a wrong SHA-256;
  - the fixture's first line was read from the first `data` event, which assumes the whole line arrives at once and
    has no bound;
  - latency p95 pooled 20 observations per run, as if they were independent samples;
  - the command exited 0 on other OSes ("not run").
- **Now:**
  - `scripts/perf/validity.mjs` gives each run a status: `ok`, `error` or `invalid` with reasons;
  - only `ok` runs enter medians, and the rest are listed under `excluded` in `summary.json` and by `compare.mjs`;
  - exit code 1 when any run is not `ok`, 2 when unavailable;
  - six distinct job ids are required and both limits are read back;
  - the sample window starts only after every job transfers with bytes (bounded at 30 s; fixture start-up, the
    completion wait and hashing stay outside it);
  - the activity evidence is described as two observations, not as continuous proof;
  - `scripts/lib/first-line.mjs` is bounded and chunk-safe, and is also used by the concurrency acceptance;
  - p95 is run-level (`scripts/perf/stats.mjs`);
  - the `method` field explains the shared-memory accounting.
- **Fixture:**
  - `fixture-process.mjs` gains `--host`, `--port` and `--public-host` (a wildcard bind without a public host is
    refused) and `/__stats`;
  - per-file requests, full and ranged responses, range starts, bytes handed to the socket, completed and aborted
    responses, and the peak of concurrently open responses;
  - the default local use is unchanged.
- **Tests (`pnpm verify`, group structure):** `first-line.test.mjs` (9), `validity.test.mjs` (7),
  `native-messaging.test.mjs` (3), `fixture.test.mjs` (6).
- **Real invalid-result run:** see the last item of [Performance baseline](#performance-baseline).

## 4. Comparison protocol made executable

[idm-comparison-protocol.md](../benchmarks/idm-comparison-protocol.md):

- **Defaults:** six files under Downova's defaults are W2a (3 active, 3 queued), separate from W2b (both clients
  configured for six at once).
- **Host budget:**
  - Downova's 8-request cap for each host is fixed, and IDM's setting is per download, so class B does not equalise
    the aggregate host budget;
  - each client's actual use (`max_open_responses`) is recorded beside every class B result;
  - the budget is keyed by host name without the port, so W3 needs two host names.
- **LAN server:** the fixture is started with its LAN address and a fixed port; `fixture-server.mjs` is not used.
- **Resume (W5):** evidence from `/__stats` (ranged starts past 0; bytes written ≤ 1.05 × size, an upper bound).
- **Status:** every IDM row remains **unrun**.

**B3.1 — CORE-06 global and per-download speed limits (plan; starts after the B2 exit):**

- **ADR 0024** (new): the limiter design.
  - **Placement:** a token bucket in `dm-backend-http`. The global bucket is shared by every download; each download
    has its own bucket, shared by all of its segments and by redirect hops. Both are charged before each body chunk is
    written (the `bytes_stream` loop in `crates/backend-http/src/transfer.rs`, which segmented transfers also use).
  - **Burst size, and interactions:** with the 8-request host budget and the 1 MiB rotation (ADR 0023); with
    resume (no refill debt carried across a restart).
  - **Accuracy target and units:** bytes/s as `u64`; 0 = unlimited.
  - **aria2:** `--max-overall-download-limit` and `--max-download-limit`, reported only as far as fixtures prove.
- **Owning modules** (following `docs/project-structure.md`):

  | Area | Change |
  |---|---|
  | `packages/contracts/schema/service-api.v1.schema.json` → generated TS; `crates/domain/src/api.rs` | `speed_limits.v1.get` / `speed_limits.v1.set` (global, nullable), a per-job `speed_limit_bps` on add and on a `downloads.v1.set_speed_limit`, examples, the closed method set |
  | `crates/domain` | validation (bounds), and the capability already listed (`SpeedLimitGlobal`, `SpeedLimitPerJob`) |
  | `crates/backend-api` | a backend method to apply limits live (global and per job), refused with `BACKEND_CAPABILITY_UNAVAILABLE` unless `supported` |
  | `crates/backend-http` | `rate.rs` (the bucket, an injectable clock), wired into `transfer.rs` / `segmented.rs`; `capabilities.rs` turns both `supported` only after the fixture proves them |
  | `crates/backend-aria2` | map to aria2 options, and report the capabilities honestly |
  | `crates/storage` | the global limit in `settings` (as `max_active_downloads`); per-job limit: migration `0010` (a jobs column), with reopen tests |
  | `crates/service` | persist first, then apply live without restarting transfers; a restart restores the limits; changes refused while the backend reports the capability unsupported |
  | `crates/cli` | `dm speed-limit [N]`, `dm speed-limit-set <JOB-ID> <N|off>`, `dm add --speed-limit` |
  | `apps/desktop` (Options, details panel, `src/i18n/messages.ts` en and bn) | the global limit in Options → Downloads; the per-download limit in the details panel; shown as unavailable with the reason when the backend does not support it |
