## Supported recovery behaviour (backend `http`)

| Situation at restart | Outcome |
|---|---|
| Running job, checkpoint valid, partial file intact | New attempt continues from the checkpoint with `Range` + `If-Range`, strict `206` checks; SHA-256 of the result matches |
| Running job, file holds bytes **past** the last committed checkpoint (crash between a write and the commit) | Those bytes are discarded (single connection: truncated; segmented: overwritten); continuation starts at the checkpoint |
| Job paused by the user | Restored paused; no request is sent until the user resumes |
| Graceful shutdown during a transfer | Checkpointed at shutdown; continues after the next start |
| Resource changed (new ETag) or server stopped honouring ranges | Validated continuation receives `200` and restarts from zero; the file is the new representation, never a splice |
| Partial file missing, truncated below the checkpoint, or modified inside confirmed data | Job **failed** with "the interrupted download could not be continued safely: …"; partial file left untouched; no destination file |
| Checkpoint from another backend, unknown format version, corrupt, oversized, or for another destination | Job failed explicitly (same prefix), checkpoint dropped |
| A file now exists at the destination | Refused; the existing file is never overwritten |
| No checkpoint (nothing confirmed yet, no strong ETag/length, aria2 backend) | Job failed as interrupted ("… before any resumable progress was saved …") |
| Cancelled or completed job | Never restarted |

Durability cadence:
- Writers sync at least every 1 s or 4 MiB.
- The service commits at most every 2 s while transferring, and always on pause and on graceful shutdown.

## Limitations and unverified cases

- **Power loss is not tested.** Only process kills are tested; power-loss safety depends on the OS and storage
  honouring `sync_data`/`fsync` and SQLite `synchronous=FULL`.
- Persistence failures are tested at the coordinator level only:
  - the backend's checkpoint fails → nothing is committed;
  - the store refuses a stale or unknown attempt.

  A full disk or an I/O error during a real SQLite commit is not injected.
- No benchmark of `synchronous=FULL` (COR-08). The desktop UI does not show recovery outcomes (B2).
- Recovery reads the confirmed data twice (import, then resume): correct but slow for very large files.
- macOS/Linux were not run locally. CI Ubuntu is red for a reason not yet read.

## Manual reproduction (any OS with Rust)

1. Serve a large file from a server with a strong ETag, or use any public file with an `ETag`. Then start an isolated
   service:

   ```bash
   cargo run -p dm-service -- --data-dir /tmp/dv --download-dir /tmp/dv-dl
   ```

2. In another terminal, add a link (with `cargo run -p dm-cli --quiet -- --data-dir /tmp/dv add <URL>`) and watch
   `… list` until a few MiB have been downloaded.
3. Kill the service hard: Task Manager → End task, or `kill -9 <pid>` (the pid is in `/tmp/dv/run/endpoint.json`).
4. Start it again with the same command. It logs "restored 1 interrupted download(s) from checkpoints". `dm list`
   shows the same job ID continuing, and the finished file's SHA-256 matches the source.
5. Variations:
   - pause before killing (it stays paused);
   - edit a byte early in `<file>.downova-part` while the service is down (the job fails with "could not be continued
     safely … modified");
   - set `DOWNOVA_CHECKPOINT_TRACE=/tmp/dv/trace.jsonl` to see every committed checkpoint.
