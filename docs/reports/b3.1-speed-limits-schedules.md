## 1. Speed limits (CORE-06): what works

- **Engine (`dm-backend-http`):**
  - one global token bucket and one per download, shared by that download's segments;
  - burst = max(rate / 4, 1 KiB), so at most about 250 ms of data;
  - writes are split into parts no larger than the burst and charged to the job bucket, then the global one;
  - live rate changes wake waiters (`watch`) without a new request;
  - waits end at once on pause, cancel or shutdown (dropped futures);
  - unlimited is one atomic load with no wait;
  - throttled segments rotate their connection after 1 MiB or 2 s when others wait.
- **Correction (a real defect found by test S05):**
  - the defect: reqwest's client `read_timeout` kept running while the engine waited for tokens, so slow limits
    failed with `NetworkOffline`;
  - the fix: the client no longer sets it, and the engine owns the per-read timeout (`transfer::within`) around
    sends and body reads only.
- **Contract (`service-api.v1`):**
  - methods `speed_limits.v1.get`, `speed_limits.v1.set` and `downloads.v1.set_speed_limit`;
  - the optional `speed_limit_bytes_per_second` on add and on snapshots;
  - values are decimal `ByteCount` strings from 1024 to 10^12, enforced by the schema pattern and by Rust;
  - `null` means unlimited (global) or "only the overall limit" (job); `0` is refused, because it is not pause.
- **Service:**
  - persist, then apply; a refused save changes neither the stored nor the effective limit (trigger test);
  - restored before recovery: the global rate reaches the backend first, and recovered attempts carry their own
    limit;
  - gated on `speed_limit_global` / `speed_limit_per_job` = `supported`, otherwise
    `BACKEND_CAPABILITY_UNAVAILABLE`;
  - a finished download's limit is refused;
  - the idempotency fingerprint is unchanged when no limit is given.
- **aria2:** both capabilities stay `unverified`, and a start with a limit is refused. There is no fixture evidence
  for aria2 limits.
- **CLI:**
  - `dm speed-limit`;
  - `dm speed-limit-set <N|off>`, with suffixes k/m/g meaning ×1000;
  - `dm job-speed-limit <JOB-ID> <N|off>`;
  - `dm add … --speed-limit N`.
- **Desktop:**
  - Options → overall speed limit;
  - download details → this download's limit;
  - KB/s, MB/s and GB/s in decimal units, with Bangla digits accepted;
  - unavailable reasons when the engine does not support limits;
  - English and Bangla, with labelled controls and status regions.

## 2. Queue schedules (CORE-08): what works

- **Domain (`dm-domain::schedule`, pure, `jiff`):**
  - one optional schedule per queue: enabled, IANA zone, 1–14 weekly windows and `skip | catch_up`;
  - overnight windows belong to their start day;
  - overlapping windows are merged;
  - DST: a boundary in a gap moves to the first instant after it; in a fold, a start takes the earlier occurrence and
    an end the later;
  - the evaluation takes an instant and returns `in_window` and `next_change`.
- **Service:**
  - **The blocker:** `schedule_window` is set or cleared at the start of every poll (at most 60 s apart) and on
    wake, before admission. It never touches `desired_state`: a window never resumes a manual pause and never starts
    a stopped queue, and the global and queue limits still apply.
  - **A window closing on running work:** a transfer with a durable checkpoint is paused like a queue stop. One
    without a checkpoint is allowed to finish (correction: resumability is judged from the durable checkpoint) and
    is re-checked at every evaluation.
  - **Catch-up:**
    - one window, for the most recent window missed within 24 h;
    - it lasts as long as the missed window, at most 6 h;
    - it is stored durably with absolute instants before it applies, so a restart neither repeats nor extends it;
    - an edit or removal clears it.
  - **Saving:** an unknown zone is refused before saving. A refused save changes nothing.
  - **Restart:** schedules are restored before recovery, so a restart outside a window starts nothing.
  - **Moves:** a moved job, and the jobs of a deleted queue, take the destination queue's stop state and schedule.
    Applying the destination's stop state on queue deletion is a fix found by the new test.
- **Contract:**
  - `queues.v1.set_schedule { queue_id, schedule | null }`;
  - `QueueInfo.schedule` and `schedule_state { in_window, next_change_at, catch_up_until }`, with UTC RFC 3339
    instants.
- **CLI:**
  - `dm queue-schedule <QUEUE-ID> <ZONE> <DAYS@HH:MM-HH:MM>... [skip|catch-up] [disabled]`;
  - `dm queue-schedule <QUEUE-ID> off`;
  - `dm queues` shows the schedule and its current state.
- **Desktop:** Manage queues → Schedule for each queue:
  - an enable checkbox;
  - the zone, preselected from the system;
  - windows with day checkboxes and From/Until times, plus an overnight note;
  - the missed-window policy, with an explanation;
  - the service's state, with the next change shown in the schedule's zone;
  - the fixed sentence that nothing downloads while the computer is off or asleep, and the policy sentence;
  - validation before anything is sent;
  - English and Bangla.

## 3. Migration and compatibility

- **SQLite schema 9 → 11:**
  - migration 10: `jobs.speed_limit_bps`, nullable, with a CHECK on the bounds;
  - the global limit is stored as a `settings` key;
  - migration 11: five nullable columns on `queues`.
- **Upgrades:** existing databases upgrade in place, and the upgrade tests from v8 and v9 pass. No downgrade: an
  older build refuses schema 11, as before for any newer schema.
- **Contract:** additive only:
  - new methods (the closed method set grows from 35 to 39);
  - new optional fields, omitted when unset;
  - older clients ignore nothing they rely on.
  - TypeScript is regenerated; `crates/domain/src/api.rs` mirrors it.
- **Behaviour without the features:** no limit and no schedule behave exactly as before, and the fingerprints are
  unchanged.
- **Dependency:** `jiff` 0.2.38 (Unlicense OR MIT), already in `Cargo.lock`. The bundled tz database is used only
  where the OS has none (Windows).

  in Manage queues.
