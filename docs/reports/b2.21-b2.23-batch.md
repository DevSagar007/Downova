## 1. Functionality completed

### N3b: deterministic restart evidence (smoke #34 Linux)

**Root cause.** This is a harness defect, not a product defect, by reasoning plus evidence.
- N3b read the "restarted" state through `until(...).catch(() => getN(...))`. When the restart was not visible
  within 30 s, the catch returned the job as it was at that moment.
- A restarted *paused* job stays paused at zero bytes: `commit_reopen` runs it only when it had failed. So 256 KiB
  can only be the pre-restart state.
- The row recorded no source, attempt or hash that could tell the two cases apart.

**Fix:**
- **Service:** the restart's trace event (`source_replaced_restart`) now records the attempt it invalidated and the
  bytes counted after the commit.
- **Smoke:**
  - N3b waits for that transition (60 s) with no fallback;
  - it asserts the same job, the invalidated attempt equal to the paused one, zero bytes, no attempt, still paused
    and the new source;
  - it then resumes and checks the SHA-256 of the replacement;
  - diagnostics record the job, attempts, transition, and expected and actual hashes.
- **Unit regression:** `a_restart_is_proven_by_its_acknowledgement_even_when_the_new_transfer_advances_before_a_poll`.
  - It checks that a running restart's acknowledgement shows zero bytes and a new attempt.
  - It lets progress advance to 256 KiB before a poll.
  - Late callbacks of the old attempt (progress, then Complete) change nothing.

### Virtualized, accessible download list (ADV12)

**Windowing** (`DownloadTable.tsx`, no new dependency):
- It renders the rows in view, 8 rows of overscan on each side, and the selected and focused rows, which are pinned
  so focus and selection never vanish while scrolling.
- Spacer rows are `aria-hidden`.
- `aria-rowcount` and `aria-rowindex` keep "row 9,412 of 10,001" understandable.
- The row height is measured at runtime, so zoom and fonts are handled.
- Page Up/Down, Home and End reach offscreen rows. Their selection and focus follow once the row is rendered.

**Unchanged behaviour:**
- search, categories, sorting, queue order (Alt+↑/↓) and Clear finished's frozen global scope operate on the whole
  list;
- the existing table, columns, tokens and look.

**Rendering work:**
- Rows are memoized by snapshot identity.
- The presentation order is recomputed only when a sorted field changes. Status sorts without its percentage, so
  progress no longer re-sorts or makes rows jump.
- `App` memoizes category, search and queue order.

**Event application:**
- Events are kept per job and applied in one indexed pass.
- They are flushed within 50 ms while visible, inside the service's 400 ms coalescing. While hidden they are flushed
  at most once per second, and at once when the window becomes visible.
- The queue is bounded by the number of jobs.
- Acknowledgements flush queued events first.
- Resnapshots still drop pending changes, and removed jobs still never return (ARCH-08).

### A product defect found by the measurements: large histories never loaded

**Symptom.** With 10,000 records, the baseline and the first optimized build both stayed empty for more than 150 s,
and `dm list` failed with exit 3.

**Cause.** The IPC transport closed any line over 1 MiB in *both* directions. A 10,000-job list or subscription
snapshot is about 4.8 MB. The desktop therefore never received its first snapshot and kept resubscribing.

**Fix** (`crates/platform/src/ipc.rs`):
- The service still refuses requests over 1 MiB.
- Clients accept responses and notifications up to 64 MiB from their own user's service.
- **Regression test:** `large_responses_reach_clients_but_oversized_requests_are_refused`.
- **After the fix:** the same 10,000-job list loads in 1.3 s (debug build).

### Completion and failure notifications (CORE-09, ADR 0022)

**How a notification is decided and shown:**
- **Where:** the service decides in its poll loop, for durable terminal outcomes only. A notification is shown on
  completion after verification and placement, or on a final failure. Accepted, transferred-but-not-finalized,
  automatic-retry and cancelled outcomes do not notify.
- **Recording:** each decision is recorded once per outcome (migration 9, `jobs.notify_state`). Notifications are shown
  by `dm-platform`'s adapter (`notify-rust` 4.18.2, behind the `notify` feature) on a blocking thread after the
  coordinator lock is released.
- **Delivery:** at most once. Restarts, replays and resubscriptions never repeat a notification. Nothing historical is
  notified, and nothing at startup.
- **Retry:** an explicit Retry or Refresh-link restart clears the decision, so the new outcome is notified.
- **Content:** the file's display name only, cleaned of control and bidi characters. Never a URL, header or path, no
  actions, and a click never opens a file.

**How the user controls it:**
- **Default:** off. Turning it on in Options or with `dm notifications-set on` shows one confirmation notification.
  Systems that ask for permission ask then.
- **Refusals:** a refused hand-off is reported once and never retried.
- **Language:** English or Bangla, following the window's language.
- **Window states:** the same behaviour whether the window is visible, hidden or closed. No WebView is kept alive for
  it.

The size growth is the notification library in the service.

**Reading these numbers honestly:**
- **Large histories:** the change for 1,000 and 10,000 records is the real result. Rendering is bounded, and the IPC
  fix makes 10,000 records usable at all.
- **Idle:** unchanged within noise. Hiding to the tray does **not** release WebView2 memory (about 155 MiB either
  way). Only closing the UI does: about 2.6 MiB remain for the service. Hidden and closed are reported separately.
- **One and three transfers:** WebView2 memory **rose** (one transfer +19 MiB, about +11 %; three +8 MiB), and CPU rose
  slightly. Per-run spread is wide: one transfer after = 179, 203, 188, 197 and 202 MiB, against 177–178 before. The
  cause is not established; event batching is the main suspect. This is recorded as an **unexplained regression to
  investigate**, not explained away.
- **Service-ready latency:** the medians rose, with large outliers (up to 14 s) in the after run. The service start
  path changed only by one migration and an unused adapter, so machine noise is likely but not proven. No
  improvement or regression is claimed for it.
- **Memory metric:** private bytes (private commit) are summable. Working set is recorded only as an over-counting sum,
  because shared pages appear in every process.
- **Scope:** one machine, Windows only. Shared CI runners would be diagnostic only. **An IDM comparison was not run**
  (IDM is not installed here). No competitive claim is made.

## 4. Remaining notification, accessibility and human-test gaps

**Notifications:**
- Whether the operating system **displays** them is not observable by Downova.
- On Windows, a toast needs an **installed** app with the AppUserModelID `com.downova.desktop`.
- The macOS permission prompt and Linux D-Bus delivery are unverified.
- All of these are human checks.

**Accessibility:** screen readers (NVDA or Narrator, VoiceOver, Orca) on the virtualized list and dialogs; 200 %
zoom and long Bangla names in the real window; reflow with very long names.

**Still not run:** human right-click, browser permission prompts, tray, OS logout, sleep and reboot, and the
earlier H1–H9 checklist (B2.15–B2.20 report §3).

**New human checks:**
- **N1:** turn notifications on, complete a download with the window visible, then hidden, then closed. Expect one
  notification each time.
- **N2:** block Downova's notifications in the OS. Expect the setting to report it once and downloads to be
  unaffected.
- **N3:** Bangla. Expect Bangla text.
- **N4:** select a notification. It may bring the app forward; it never opens the file.
