## What was built

| Piece | Implementation |
|---|---|
| Sidecars | `scripts/package.mjs` builds release `dm-service` and `dm` (`cargo build --release --locked`), stages them as `apps/desktop/src-tauri/binaries/<name>-<host-triple>[.exe]` and runs `tauri build` with `src-tauri/tauri.package.conf.json` merged in (`bundle.externalBin: ["binaries/dm-service", "binaries/dm"]`). Tauri strips the triple and installs the sidecars **next to the main executable** on every platform. The overlay keeps `externalBin` out of the base config, so ordinary `cargo build`/clippy/tests do not need staged binaries |
| Bundles | Windows: NSIS + MSI (x86_64). macOS: `.app` + `.dmg` (arm64 on `macos-latest`), ad-hoc signature (`signingIdentity: "-"`), not notarised. Linux: `.deb` + AppImage (x86_64), built on Ubuntu 22.04 as the glibc baseline |
| Outputs | `dist-packages/<os>-<arch>[-smoke-test]/` with the installers, `SHA256SUMS.txt` and `build-info.json` (triple, bundles, signing, `aria2_bundled: false`, commit) |
| aria2 | never bundled (ADR 0005, REL-05) |
| Service discovery | `apps/desktop/src-tauri/src/service.rs`, Tauri command `service_connect` (the only command): reads the private endpoint and sends `service.v1.hello` (3 s bound); reuses a compatible service; reports an incompatible API version without replacing it; otherwise starts the packaged `dm-service` beside the executable **detached** (Windows `DETACHED_PROCESS \| CREATE_NEW_PROCESS_GROUP \| CREATE_NO_WINDOW`; Unix own process group), reaps it if it exits, and waits up to 20 s for `hello`. A concurrent start is settled by the service's single-instance lock (exit code 3 → keep waiting); a stale endpoint is replaced by the winning service. User-only IPC is unchanged |
| UI | `TauriServiceClient` (only inside the Tauri shell; the plain-browser dev mode keeps the foundation client). The status bar shows "Connected to download service" from the real `hello`. Download commands stay **unavailable** with a new honest reason ("the service is running, but this command is connected to it in a later milestone"); design unchanged |
| CLI | `dm hello` (versions, backend id, capability report; `--json` supported) |
| Test hook | cargo feature `smoke` (test builds only): after the main window loads, the app writes `{window, service, sidecar, pid}` to `$DOWNOVA_SMOKE_FILE`. Release packages without `--smoke` contain no hook |
| Workflow | `.github/workflows/package-smoke.yml` (separate from `ci.yml`): Windows x86_64, macOS arm64, Linux x86_64 (Ubuntu 22.04); builds smoke-test packages, runs the packaged smoke test (Linux under `xvfb-run`), uploads `downova-<label>-smoke-test-<sha>` artifacts (packages, SHA-256 sums, `results.json`, `summary.md`, logs, screenshots), retention 14 days, no releases |

## Packaged-app smoke test (`scripts/smoke/packaged-smoke.mjs`)

Uses only the binaries inside the installed or unpacked package, isolated `DOWNOVA_HOME` / `DOWNOVA_DOWNLOAD_DIR` in a
temporary directory, `DM_ARIA2_PATH` pointing to a non-existent file, and an in-process controlled HTTP fixture
(deterministic payloads, strong ETag, ranges, optional slow body).

- **Install:** Windows NSIS per-user silent install (`/S /D=<tmp>`) plus an MSI administrative extract (`msiexec /a`,
  no system install); macOS `.dmg` mounted and the `.app` copied; Linux `.deb` with `sudo dpkg -i` when available
  (otherwise `dpkg-deb -x`), plus AppImage `--appimage-extract` to check the sidecar.
- **A:** packaged `dm-service` alone → `dm hello` reports backend `http`; `dm list`; fixture download → SHA-256.
- **B:** packaged desktop (no service running) → window loads; its own handshake starts the packaged service;
  `dm hello` against that service.
- **C:** a slow transfer is running → the desktop is closed (Windows `taskkill` = WM_CLOSE, macOS `osascript quit`,
  Linux SIGTERM) → the service process is still alive → the download completes with the expected SHA-256.
- **D:** uninstall (NSIS uninstaller, `dpkg -r`, removing the `.app`).
- **Screenshots** never capture the whole desktop on a developer machine: Windows captures only the Downova window
  (DWM frame bounds); macOS/Linux take a full-screen capture only on CI runners. (The first local run captured the full
  screen, including unrelated private windows; that image was deleted and the capture restricted.)

## Remaining (manual or later)

- Clean-machine install/uninstall on fresh Windows 10/11, macOS 13+ and Ubuntu 22.04/24.04 (the local machine has the
  development toolchain installed); upgrade over an older install; orphan-process and registry checks (REL-01).
- Code signing (Windows Authenticode), Developer ID signing and notarisation (macOS), SmartScreen/Gatekeeper behaviour
  of the current unsigned builds — blocked on signing identity and the project licence.
- A public HTTPS download through the packaged app (platform trust store), proxies, and large files on slow networks.
- Intel macOS: no runner and no runtime test; not claimed.
- Service autostart at login and an explicit "Exit and stop downloads" (ARCH-01) — not implemented.
- The desktop UI does not yet issue download commands (B2).
