## What was built

| Area | Implementation |
|---|---|
| Crate | `crates/backend-http` (`dm-backend-http`), depends on `dm-domain` and `dm-backend-api` only |
| Stack | reqwest 0.13.5 (`default-features = false`, `rustls-no-provider`, `stream`), rustls 0.23.46 (`ring`), rustls-platform-verifier 0.7.1, Tokio 1.54 |
| Trust | a rustls `ClientConfig` built by the backend: `ring` provider + platform verifier (OS trust store). Fixture CAs only through `HttpConfig.extra_roots` (`Verifier::new_with_extra_roots`). Verification is never disabled; the OS store is never modified |
| Transport | HTTP/1.1 only (ALPN `http/1.1`), no proxy, no cookie store, no referer, no decompression features, `retry::never()`, connect timeout 15 s, read timeout 30 s |
| Redirects | `Policy::none()`; followed manually, at most 10 hops; each hop's scheme gated by the capability report (`http`→`Http`, `https`→`Https`, anything else refused) |
| Scoping | credential headers (`is_sensitive_header`) and validators (`If-Match`, `If-None-Match`, `If-Range`, `If-Modified-Since`, `If-Unmodified-Since`) are sent only while the hop has the original origin; URL userinfo is converted to Basic auth by reqwest and not carried to other origins |
| Responses | final status must be `200`; `Accept-Encoding: identity` and any non-identity `Content-Encoding` refused; byte count checked against `Content-Length` (short → `NETWORK_OFFLINE`, long → `INVALID_RANGE`) |
| Errors | 401/407 `AUTH_REQUIRED`; 403/404/410 `LINK_REFRESH_REQUIRED`; 412 `REMOTE_CHANGED`; 416/206 `INVALID_RANGE`; 408/429/5xx `SERVER_BUSY` with `Retry-After` in `BackendError.retry_after`; TLS failures `TLS_HANDSHAKE_FAILED` with the reason (untrusted issuer, wrong host name, expired, …). Details never contain URLs; `reqwest::Error` is never formatted |
| Files | bytes stream through a 256 KiB buffer into `<name>.downova-part`, created with `create_new`; the destination must not exist. On success: flush, `sync_all`, then publish with a hard link (fails if the destination exists) or, where links are unavailable, a checked rename |
| Control | pause/remove/shutdown signal the task and wait for it (bounded 10 s, then abort): network and disk activity stop before the call returns, and the buffered bytes are flushed so the partial file equals the reported progress. `resume` with partial bytes → `BACKEND_CAPABILITY_UNAVAILABLE`; with zero bytes it restarts. `discard` deletes only the attempt's `.downova-part`, never a completed file |
| Refused | `max_connections > 1`, `Range`/`If-Range` request headers (`BACKEND_CAPABILITY_UNAVAILABLE`) |
| Service | `dm-service --backend http|aria2` (default **`http`** since [ADR 0005](../decisions/0005-default-backend.md); `--aria2` only with `aria2`). The service binary installs the ring provider as the process default (see "Defect found") |
| Fixtures | the controlled fixture server and test PKI moved to `crates/test-fixtures` (`dm-test-fixtures`, dev-dependency only), shared by aria2 and the HTTP backend |

### Defects found while building the matrix

1. **Fixture TLS flush (test infrastructure).** T01 hung in 2 of 5 runs at 2 031 616 of 2 097 152 bytes. The fixture
   server never flushed after writing a body; tokio-rustls keeps the last records buffered until a flush, so on a
   kept-alive TLS connection the tail could stay unsent. Fixed by flushing after every response. The aria2 matrix uses
   the same server and was re-run after the fix.
2. **TLS errors classified as network errors.** hyper-rustls nests `rustls::Error` inside two `io::Error`s, and
   `io::Error::source()` skips a custom payload. The classifier now descends into `io::Error::get_ref()`. T02–T04 now
   report `TLS_HANDSHAKE_FAILED` with the reason.
3. **Progress ahead of the disk.** On stop, the write buffer was dropped, so the partial file could be shorter than the
   reported progress (X01 first showed 0 B). The task now flushes before acknowledging a stop.
4. **Secret in `Debug`.** The backend's `Debug` printed the raw request URL. The attempt now formats a redacted source.
5. **Feature unification panic in `dm-service`.** Linking both backends unifies reqwest features: the TLS support enabled
   for `dm-backend-http` (without a bundled provider) also applied to the aria2 adapter's loopback RPC client, and
   `dm-service --backend aria2` panicked at startup ("No rustls crypto provider is configured"). Found by the CLI
   real-service test. The service binary now installs `ring` as the process default before anything else.

## Limitations

- Windows only so far; macOS (Security.framework) and Linux (webpki + system roots) verifier paths need CI.
- Public HTTPS sites are not exercised by tests (no external network); production trust is the platform verifier.
- No resume of partial data and no segmentation; interrupted transfers restart from zero via the service.
- Unknown-length truncation (H05) is undetectable without a trusted size or hash.
- Revocation checking is whatever the platform verifier does on each OS; not tested here.
- New dependency tree (reqwest, hyper, rustls, rustls-platform-verifier, ring) needs the licence and advisory review
  (REL-03, REL-05) before shipping.

## Validated resume (second increment, 2026-10-25)

### Design

- **Identity**, fixed by the first `200`: strong ETag (a weak `W/` or missing tag is recorded as none), representation
  length (`Content-Length`), identity encoding (checked), and the final URL after redirects.
- **Checkpoint**, written when the task stops: the confirmed offset (bytes flushed to `<name>.downova-part`) and the
  SHA-256 state of exactly those bytes. Pause flushes before acknowledging; the service now reports the backend's
  confirmed count in the pause acknowledgement.
- **Resume** (`DownloadBackend::resume` on a paused attempt with confirmed bytes):
  1. requires a strong ETag and a known length, else `BACKEND_CAPABILITY_UNAVAILABLE` ("can only restart from the
     beginning"), no request sent, job stays paused;
  2. re-reads the partial file: length must equal the offset and SHA-256 must equal the checkpoint, else
     `INVALID_RANGE` ("deleted/truncated/extended/modified outside Downova"), no request sent;
  3. one request to the **final URL** (no redirects followed during resume) with `Range: bytes=<offset>-`,
     `If-Range: <ETag>` and `Accept-Encoding: identity`; caller credentials and validators only if the final URL has
     the original origin;
  4. a `206` is appended only if: identity encoding, the same strong ETag, `Content-Range: bytes <offset>-<len-1>/<len>`
     exactly, and `Content-Length` (if present) equal to the span. Before the first append the file length is checked
     again. Each chunk is bounded by the known length;
  5. a `200` (validator mismatch or range ignored) is **never appended**: the file is truncated and the full body is
     written from zero under its new identity;
  6. 3xx → `REMOTE_CHANGED` ("moved; restart"); 416 → `INVALID_RANGE`; 412 → `REMOTE_CHANGED`; others keep their class
     and `Retry-After`.
- Validated bytes of a cut `206` are flushed, so the partial file always equals the reported progress.
- Automatic retries after a *failure* are unchanged: the service discards and starts a fresh attempt from zero. Resume
  is for user pause/resume within a running service; durable resume across restarts is B1.

- A server that keeps the same strong ETag for different content (V05) defeats any validator-based scheme; supply a
  trusted SHA-256 when it matters.
- Resume requires a strong ETag and a length; many dynamic endpoints provide neither and can only restart.
- `Last-Modified` dates are not used as validators (weak by nature).
- Resume after a service restart is not possible yet (in-memory jobs; B1).

## Validated segmentation (B0.4.3, 2026-10-25)

### Design (`crates/backend-http/src/segmented.rs`)

- **When:** the probe `200` gave a strong ETag and a length, `max_connections > 1` (the service asks for 4 when
  `SegmentedHttp` is supported), and every segment would be ≥ 1 MiB. Segments = `min(max_connections, 4,
  length / 1 MiB)`, at least 2. Otherwise the documented single-connection path runs on the probe's own `200`
  (small files, no/weak ETag, no length, one connection requested).
- **Plan:** `split(length, n)`: contiguous, non-overlapping ranges covering `0..length` exactly (checked u64
  arithmetic; unit-tested up to `u64::MAX`). The probe's body is not used; every byte comes from a validated `206`.
- **Workers:** one per incomplete segment, each with its own file handle (positioned writes, no shared cursor) and a
  128 KiB buffer (memory ≤ 4 × 128 KiB). Each sends `Range: bytes=<first>-<last>`, `If-Range: <ETag>`,
  `Accept-Encoding: identity` to the final URL; caller credentials only for the original origin; no redirects.
- **Before any byte of a segment is written:** status `206`, exact `Content-Range` for the requested range, the original
  total length, the same strong ETag, identity encoding, matching `Content-Length`; the body is bounded by the segment
  length and must fill it.
- **Coordination:** a failure (or a `200`) halts every worker; the orchestrator **waits for all of them** (each flushes
  and reports its confirmed bytes and SHA-256 state) before deciding:
  - pause/remove → per-segment checkpoint, stopped;
  - any `200` (validator mismatch or ranges ignored) → the whole file restarts from zero on one connection with a fresh
    probe, never spliced;
  - other violation → the classified failure, nothing published;
  - all complete → `sync_all`, publish without overwrite.
- **Progress** counts confirmed and in-flight bytes per segment, never the preallocated file size; on a failed flush the
  unconfirmed bytes are subtracted again.
- **Pause/resume:** the checkpoint keeps `start`, `end`, `done` and the SHA-256 state per segment. Resume re-reads every
  confirmed region (length = total, hashes equal) and starts workers only for incomplete ranges, from
  `start + done`.
- Remove/cancel waits for every worker; the attempt is then gone, so no late worker can write or revive it.

### Defects and test fixes found while building it

- **G15 race assumption:** the first version expected "cancel after all bytes were counted" to always publish. A worker
  can still be between its last chunk and end-of-body, so the cancel may legitimately stop it first (observed once in
  five runs). The behaviour was correct; the test now separates the deterministic side (remove after `Complete`) from
  the racing side.
- **Stuck test harness:** a failing assertion left `dm-service` running and the harness hung on its pipes; the process
  test now kills the service on drop.
- Earlier tests that asserted "segmentation refused" (X05) and the service/CLI tests that assumed one connection were
  updated to the new, validated behaviour; the cut-connection service case uses a 1.5 MiB file so it still exercises the
  single-connection path.

### Integration

- `http_backend_process.rs` (real `dm-service --backend http`): `hello` reports `SegmentedHttp` supported; a 3 MiB
  download used a probe + 3 validated segments, SHA-256 match; 503 + `Retry-After` then probe + segments, SHA-256
  match; pause at 1 064 960 B across 4 segments → no writes while paused → resume at in-segment offsets → SHA-256 match;
  cancel → partial byte-identical after acknowledgement.
- `real_service.rs::cli_pause_resume_with_http_backend`: `dm pause` / `dm resume` on a 6 MiB file: the four segment
  ranges plus four continuation ranges, all with `If-Range`, SHA-256 match.

### Limits

- Lying validators (G06) defeat any client-side check; a trusted SHA-256 is the only protection.
- Per-host and global connection limits across jobs (CORE-02: ≤ 8 per host, 3 active files) are not implemented; the
  per-file cap is 4.
- No speed-up claim: REL-04 benchmarks have not been run.
- Segments are fixed at the start; no work stealing or dynamic re-splitting.
- Windows-only evidence for B0.4.3 until CI runs it.
