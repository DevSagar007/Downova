## Method

- **Fixture server** (`crates/backend-aria2/tests/support/`): loopback HTTP/HTTPS with scriptable routes (range
  handling, ETag, Content-Length on/off, truncation, Content-Encoding, Content-Disposition, redirects, scripted status
  sequences with Retry-After, slow bodies, body swaps during a transfer). Every request is logged with its headers, so
  tests check `Range`, `If-Range`, `Authorization` and `Cookie` as sent.
- **Oracle:** the SHA-256 of the file against the expected payload. When old and new versions have the same length, a
  prefix/suffix comparison names the mixture (`MIXED: starts with A, ends with B`).
- **Classification:**
  - **safe success:** engine reports complete and the bytes are exactly the expected payload;
  - **safe failure:** engine reports failure with a classified `ErrorKind`; no false completion;
  - **unsafe:** engine reports complete with wrong or mixed bytes, or leaks a credential;
  - **not tested:** the scenario could not be exercised honestly on this host.
- **Two configurations:**
  - **engine** (`max_tries = 5`, the B0.1 default): raw aria2 behaviour including internal retries;
  - **production** (adapter defaults after B0.4: `max_tries = 1`, `--continue=false`, credential headers refused,
    one connection): what `dm-service` runs.
- Unsafe engine outcomes are **asserted as unsafe**: if aria2 behaviour changes, the test fails and the decision must be
  revisited. No check was weakened and certificate verification was never disabled.

## Review fixes (same day)

A review of the B0.4 implementation found and fixed:

1. **Stale resume gate (service).** `resume` checked the byte count from the last 400 ms poll. A pause between two polls let a
   partial transfer through to aria2's validator-less resume (the C06 path). The gate now reads the engine's current
   progress first. Regression: `resume_gate_uses_fresh_engine_progress_not_the_last_poll` (failed before the fix).
2. **Status parsing.** `http_status` took the first `status=` in aria2's message, which begins with the request URL, so
   `?status=200` in a URL changed the classification. It now takes the last one. Regression:
   `a_status_parameter_in_the_url_does_not_change_the_classification`.
3. **New evidence:** D04 and D05 (above).

## Fixes made in B0.4

All in the adapter or classification; no engine change.

1. `max_tries` 5 → 1: removes aria2's unvalidated internal resume (C01–C04 → C08 safe).
2. `--continue=true` → `--continue=false`: no append to foreign files (K03).
3. Credential headers refused unless an explicit unsafe test flag is set (D02 → D03).
4. `classify(code, message)`: distinguishes 401/403/410/429/5xx behind aria2 code 22, 503 (code 29), TLS handshake
   failure, and interrupted transfers ("No URI available.", code 1). Only status digits and fixed markers are read;
   the message itself (it contains the raw URL and token) is never forwarded.
5. New `ErrorKind`s `SERVER_BUSY` (retryable, wait) and `TLS_HANDSHAKE_FAILED` in the contract.
6. `capabilities::report(max_tries)`: `Http` supported only with `max_tries = 1`.

## TLS backend and bundled libraries

`aria2c --version` of the pinned build:

```text
Enabled Features: Async DNS, BitTorrent, Firefox3 Cookie, GZip, HTTPS, Message Digest, Metalink, XML-RPC, SFTP
Libraries: zlib/1.3 expat/2.5.0 sqlite3/3.43.1 GMP/6.3.0 c-ares/1.19.1 libssh2/1.11.0
Compiler: mingw-w64 8.0.0 (alpha) / gcc 10-win32 20220113
```

- **TLS backend: WinTLS (SChannel), not OpenSSL.** No TLS library is listed; the binary imports `Secur32.dll` and
  `CRYPT32.dll` and contains no OpenSSL version strings. Upstream's `mingw-config` for release-1.37.0 configures
  `--without-openssl --without-gnutls`. The archive's `LICENSE.OpenSSL` file is a leftover; the B0.1 report's claim
  is corrected.
- Consequences: trust comes from the Windows certificate store and TLS fixes come from Windows Update; `--ca-certificate`
  is not honoured (T01).
- **Dated libraries** (checked against upstream advisories, 2026-10-21):
  - **libssh2 1.11.0:** 1.11.1 contains the Terrapin (CVE-2023-48795) mitigation. Affects SFTP only; SFTP is not a
    supported capability.
  - **expat 2.5.0:** predates fixes for CVE-2023-52425, CVE-2024-28757 and CVE-2024-45490 (fixed by 2.6.3). Used for
    Metalink/XML-RPC parsing; the adapter uses JSON-RPC and no Metalink.
  - **c-ares 1.19.1:** predates 1.27.0 (CVE-2024-25629, reading `/etc/resolv.conf`-style config). Applicability to the
    Windows build is limited but not proven absent.
  - Verdict: acceptable for local test fixtures; **not acceptable to ship**. REL-05 requires a rebuilt sidecar.

## Limitations

- Windows only. T01 success on an OpenSSL/GnuTLS build, and every other case on macOS/Linux, need a CI run.
- K02 did not exercise a non-zero-offset crash resume.
- Retry-After/backoff is implemented in the service since B0.4.1, but aria2 cannot report `Retry-After`, so with aria2 only backoff is exercised; Retry-After itself is proven with the fake backend.
- Bangla filenames are covered only as an unsafe server suggestion that is ignored (N01); normalisation is E04 (B1).

## B0.4.1 engine remediation (2026-10-25)

Same host, toolchain and aria2 build. HTTPS failures and resume failures were investigated separately.

### HTTPS: the cause of T01

- **TLS backend:** the adapter now reads it from `aria2c --version` (`binary::parse_tls`): no OpenSSL/GnuTLS in
  "Libraries:" plus the `HTTPS` feature means the platform stack. T00 confirms **WinTLS (SChannel, OS trust store)** for
  the pinned build.
- **Cause:** upstream `src/WinTLSContext.cc` (release-1.37.0) implements `addTrustedCACertFile` as a warning
  ("TLS CA bundle files are not supported. The system trust store will be used.") and `return false`. aria2 then
  continues without the CA. Peer verification uses SChannel automatic validation with chain revocation checks
  (`SCH_CRED_AUTO_CRED_VALIDATION | SCH_CRED_REVOCATION_CHECK_CHAIN`). This is not a bug in our fixture or in
  certificate generation: the build cannot load a CA file.
- **Fix:** `Aria2Backend::launch` refuses a `ca_certificate` when the build cannot honour it
  (`BACKEND_CAPABILITY_UNAVAILABLE`, "this aria2 build uses WinTLS … and ignores CA bundle files"), instead of
  silently using a different trust store than configured. The `Https` capability note now names the TLS backend.
- **Evidence:** `tls_backend_is_read_from_the_banner` (unit, banners from the pinned Windows build, Ubuntu GnuTLS and an
  OpenSSL build); T00; T01 and T03 now assert the launch refusal on WinTLS and still expect success / host-name
  rejection on OpenSSL/GnuTLS builds; T02 unchanged (self-signed rejected, no HTTP request).
- **Status:** `Https` stays **unverified** for aria2. On Windows a trusted success cannot be proven without adding a
  test CA to the OS trust store, which the tests never do. Public HTTPS uses the Windows store, which is untested here.

### If-Match through the existing header interface

Every case passes `If-Match: "v1"` through `TransferRequest.headers` (aria2 `header` option), with engine-internal
retries on (max-tries 5) to exercise the resume path that would be unlocked. The fixture evaluates `If-Match` with
strong comparison (RFC 9110) unless told to ignore it. A new mapping classifies `status=412` as `REMOTE_CHANGED`.

| Case | Server behaviour | Outcome | Notes |
|---|---|---|---|
| M01 | unchanged, cut once | safe success | 2 requests, both with If-Match; internal resume byte-exact |
| M02 | same-length change after a cut, 1 conn | safe failure `INVALID_RANGE` | the resumed request got 412, but aria2 reported only "No URI available." (code 22, **status dropped**) |
| M03 | same-length change, 4 conns | safe failure `INVALID_RANGE` | every segment request carried If-Match; no mixing |
| M04 | same-length change, server **ignores** If-Match | **unsafe** | MIXED A/B reported complete; aria2 never checks the response ETag |
| M05 | wrong Content-Range on resume | safe failure `RANGE_UNSUPPORTED` | |
| M06 | ETag already changed before the first request | safe failure `REMOTE_CHANGED` | status visible on the first request only |
| M07 | change between pause and resume | safe failure `INVALID_RANGE` | status dropped, as in M02 |
| M08 | weak ETag, unchanged | safe failure `REMOTE_CHANGED` | strong comparison never matches a weak tag: unusable |
| M09 | origin redirects to a CDN with its own ETag | safe failure `REMOTE_CHANGED` | If-Match is forwarded cross-origin, so redirected downloads always fail |
| M10 | unchanged, 4 conns | safe success | 4 requests (3 ranged), all with If-Match |

Results were identical in two consecutive runs.

**Verdict:** If-Match protects only against servers that evaluate it on every request. M04 shows the remaining unsafe
outcome, and aria2 offers no way to detect it: it neither compares the response ETag nor sends If-Range. A preflight
(HEAD or a deliberately failing If-Match probe) cannot prove that later requests to another node, a CDN or a retry
evaluate the condition. M09 also shows that If-Match breaks every cross-origin redirect. **`ResumeStrongValidator` and
`SegmentedHttp` stay unsupported for aria2**, and the service does not add If-Match.

### Service-owned retry (COR-04)

- Policy in `dm_domain::retry`: only `NETWORK_OFFLINE` and `SERVER_BUSY` are retried; at most 3 retries;
  `Retry-After` honoured exactly up to 15 minutes, otherwise no automatic retry; else backoff 2 s × 2ⁿ capped at 60 s with
  equal jitter. `parse_retry_after` handles delta-seconds and IMF-fixdate.
- `BackendError.retry_after` carries a server-requested wait from engines that can see it. **aria2 cannot** (no response
  headers over RPC), so with aria2 the service always uses backoff.
- Before a retry the service calls the new `DownloadBackend::discard`, which removes the transfer and deletes its partial
  file and `.aria2` control file, so the next attempt starts from zero. Without it aria2 would resume from the control
  file without a validator. A failure to discard fails the job instead of retrying.
- During a 429/503 cool-down the job is `queued` with the `rate_limit_cooldown` blocker and the last error. Pause,
  resume and cancel respect the cool-down.
- **Evidence:** domain tests (`only_transient_kinds_are_retried`, `retries_are_bounded`,
  `retry_after_is_honoured_exactly_and_capped`, `backoff_grows_exponentially_with_equal_jitter_and_a_cap`,
  `retry_after_values_parse`); service tests with paused time
  (`server_busy_waits_for_retry_after_then_starts_a_fresh_attempt`,
  `network_failure_uses_bounded_backoff_and_then_gives_up`,
  `permanent_failures_and_overlong_retry_after_are_not_retried`, `pause_and_cancel_during_a_cooldown_are_respected`); real
  service + aria2 `transient_failures_are_retried_by_the_service_from_zero`: a 503 and a connection cut halfway each
  produced one failed attempt and one retry, **no `Range` on the retry**, completed, SHA-256 match.

### Decision

aria2 cannot pass the resume and segmentation correctness tests through its existing interface. That evidence is
recorded in [ADR 0004](../decisions/0004-rust-http-backend-prototype.md): a small Rust HTTP backend prototype (Tokio,
reqwest, rustls) behind the existing `DownloadBackend` trait. No capability was promoted in B0.4.1.

### Root causes

1. **Unreaped engine (K01, service kill test).** The adapter's `Child` was waited on only in `shutdown()` and during
   startup. A killed aria2 therefore stayed a **zombie** on Unix: exited, but not reaped, and `kill -0 PID` succeeds
   for a zombie. Windows has no zombies (`tasklist` stops listing a terminated process), which is why only Windows
   passed. Determined from the code path, not from a Unix reproduction (no Unix host here). The tests now print the
   process state (`running` / `zombie` / `gone`), so the next CI run records which one it is.
2. **C05 race.** The test switched the route to version B after it saw the *first* request. On aria2 1.36.0 (ubuntu-22.04)
   all segment requests evidently arrived before that switch, so every byte came from A: the change scenario never
   happened, and the `SafeSuccess` was not evidence about segmented change detection. The 1 MiB truncation also never
   triggered with 768 KiB segments.
3. **C07 race.** Same pattern without a slow body: aria2 re-requested after the cut before the test swapped in the gzip
   representation, so the continuation got identity bytes again. The encoding switch was never exercised.

### Fixes

1. **Engine ownership and reaping** (`crates/backend-aria2/src/lib.rs`): a watcher task owns the `Child` and waits on it
   for its whole life, publishing the exit through a `watch` channel, so the process is reaped as soon as it exits for
   any reason. `shutdown()` and `Drop` ask the watcher to kill; `shutdown()` returns only after reaping. Every RPC
   reports `SERVICE_UNAVAILABLE` ("download engine exited unexpectedly (…)") once the engine has exited, and a
   transport failure waits up to 2 s for the watcher to confirm an exit. New API: `wait_exit(limit)`, `exit_status()`.
2. **Bounded synchronization in the kill tests:** K01 kills only once bytes are flowing (bounded loop instead of a fixed
   1.2 s sleep), then waits on `wait_exit` (≤ 10 s) instead of a 500 ms sleep, and asserts that the exit was observed,
   that the engine is not alive, and that the job was not completed. `pid_alive` is unchanged and still treats a zombie
   as alive. The service test also starts the kill only after bytes are reported, and the service reports the loss only
   after the exit is observed.
3. **Deterministic fixture transitions** (`tests/support`): `Route::then_after(n, next)` replaces the route after
   `n` requests, atomically with request accounting; every logged request records the `tag` of the representation that
   answered it.
   - C01–C05, C08: version A answers exactly the first request, version B every later one.
   - C06: pause only after ≥ 256 KiB arrived (bounded), then switch.
   - C07: identity first (cut at 1 MiB), gzip for every later request.
   - M01–M05: same transition mechanism.
4. **Scenario proof before conclusions:** each case asserts `Served::proven()` (the original served a request and the
   changed representation served at least one *ranged* request) before judging the outcome. C08 asserts exactly one
   request (no retry with max-tries 1).
5. **C07 assertion:** after the proof, the outcome must be a safe failure, or a completion whose bytes equal the identity
   representation exactly. Anything else panics as unsafe. On the pinned 1.37.0 it is a safe failure
   (`RANGE_UNSUPPORTED`); the assertion was not widened to accept unproven or wrong bytes.
6. **C05 assertion is unchanged** (`Unsafe`): aria2 compares no validator in any version, so with the scenario proven
   a splice is expected on 1.36.0 too. If 1.36.0 behaves differently, the run will show it with proof attached.
