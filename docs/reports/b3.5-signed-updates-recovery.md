## 2. What now works

**In the desktop app (Help → Check for updates…):**
- A build without a trusted updater configuration says **"Updates are not configured"** (also for `.deb`/`.rpm`
  packages, "updated by your package manager", and unpackaged development builds). It never says "up to date".
- With a configuration: Check → Download → **Verified** (only after the plugin verified the signature and the
  signed version) → Prepare (the service holds running downloads, checkpoints and backs up) → Install now (a second
  confirmation) → the service stops, the installer starts.
- Cancel is available until installing starts; it releases the service and resumes what it held.
- Automatic checking is **off by default** and opt-in in the dialog; it only checks, never downloads or installs.
- **Recovery required** appears when the new version could not open the data; it offers exactly "Try again" and
  "Restore the pre-update backup" (with a confirmation), never an automatic restore.
- English and Bangla text for every state (54 keys each).

**In the service:**
- `service.v1.prepare_update` / `service.v1.cancel_update` with a bounded lease (10 minutes):
  - new work is refused while held (add, resume, retry, refresh, reconnect: "an update is being prepared");
  - running transfers are stopped with their checkpoints committed and their **desired state unchanged**: a
    manual pause stays paused, a stopped queue stays stopped;
  - a `VACUUM INTO` backup is synced, reopened read-only and checked (integrity, schema version, job count,
    SHA-256), and recorded in `update/pending.json`;
  - any failure releases the lease and resumes the held work; the lease also expires on its own.
- **At startup:** a pending marker for the running version is accepted (`update/last.json`: installed) and held
  work resumes only then; a marker for another version is closed as `not_installed`.
- **A failed migration or open** writes `update/recovery.json` (operation, schema versions, what failed, the
  matching backup) and exits with code **6** instead of serving.
- **`dm-service --restore-update <operation>`** restores only a backup that still matches its checksum, passes the
  integrity check and has a schema this binary can open; the replaced files are set aside, never deleted. It exits
  0 on success and 5 when the restore is refused.

**Packaging:** `scripts/package.mjs --updater-config FILE` builds updater artifacts (`.sig`) from a trusted config
plus a separately supplied signing key; `--update-fixture` additionally allows loopback HTTP and compiles the
`update-fixture` feature. A normal package refuses a fixture config and refuses to build while updater signing
variables are set.

## 4. Security properties and how they are enforced

- **Trusted configuration only.** `plugins.updater` lives in a build-time config merged by `tauri build --config`
  and compiled in. The shell registers the plugin only if `check_config` accepts it: a public key,
  `requireSignedVersion: true`, no `dangerousAcceptInvalid*`, HTTPS endpoints (loopback HTTP only in a fixture
  build). The webview never supplies a URL, key, path or installer, and no `updater:*` permission is granted to it;
  it calls seven fixed `update_*` commands with an operation ID only.
- **Verification by the plugin:** minisign over the artifact against the compiled key, then the trusted comment's
  `version:` must equal the announced version (`requireSignedVersion`). Non-newer versions are not offered.
- **No downgrade without a verified backup.** The only restore path is the explicit `--restore-update` with a
  checksum-checked, integrity-checked backup. Binaries are never downgraded by Downova.
- **Backups contain no vault secrets:** sealed URLs and credential references only; the data key and remembered
  sign-ins stay in the OS store and are not rotated during an update.
- **Redaction:** shell messages are fixed and URL-free (`classify`); the service's update records hold operation
  IDs, versions, schema numbers and checksums only.
- **Disposable test keys:** `scripts/update/verifier-fixture.mjs` generates two key pairs with the pinned Tauri CLI
  in a fresh `mkdtemp` folder with a random per-run password, and deletes the folder afterwards. No key is in the
  repository.
