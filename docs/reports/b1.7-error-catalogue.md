## 1. Linux CI repair (E04)

**Cause.** The test fixture created `Report.PDF` and three jobs announced `report.pdf`. The test expected `report (1).pdf`
… `report (3).pdf`, which is only true on a case-insensitive folder. On ext4 `report.pdf` is free, so Linux correctly
produced `report.pdf`, `report (1).pdf`, `report (2).pdf`.

**Production behaviour is unchanged and matches ADR 0011 §8.** Existing directory entries collide as the file system
decides (`symlink_metadata`). Names reserved by other jobs are compared NFC + lower case on every OS. Placement never
overwrites (ADR 0008).

**Tests** (`crates/service/src/core/tests.rs`):
- `simultaneous_jobs_announcing_one_name_get_distinct_names`: the existing file now has exactly the announced name,
  so every file system reports the collision. It expects `report (1).pdf` … `report (3).pdf`.
- `an_existing_name_differing_in_case_follows_the_file_system`: `Report.PDF` exists. The test first measures the
  temporary folder (creates `CaseProbe`, looks up `caseprobe`).
  - Case-insensitive: it expects `report (1).pdf` … `report (3).pdf`.
  - Case-sensitive: it expects `report.pdf`, `report (1).pdf`, `report (2).pdf`.
- Both keep the assertions for distinct staging names (`x`, `x (1)`, `x (2)`) and for the untouched user file.

**Runs.**
- Case-insensitive branch: Windows NTFS default folder, PASSED.
- Case-sensitive branch: a Windows NTFS folder with the per-directory case-sensitive flag
  (`fsutil file setCaseSensitiveInfo <dir> enable`, `TMP`/`TEMP` pointed at it). PASSED, and all 58 `dm-service`
  unit tests passed there.
- This is not a Linux run. Linux (ext4) evidence comes from CI after a push.

## 2. Error catalogue audit (CORE-11)

### Meaning of the fields (now documented in `ErrorData` and the schema)

- `retryable`: the cause is transient, so the same request may succeed later without any change. It is **not** a promise
  of an automatic retry.
- Automatic retries are a separate service policy:
  - transfers: `retry::is_auto_retryable`, i.e. `NETWORK_OFFLINE` and `SERVER_BUSY`, at most 3 retries, honouring
    `Retry-After` up to 15 min;
  - disk: the disk recheck (every 2 s) for `DISK_FULL` and `VOLUME_MISSING` while the job waits with a blocker.
- `next_action`: the step the user may take. Clients choose their own text from `kind` and `next_action` and never
  parse `detail`, which stays English, sanitized and locale-neutral in meaning.

### Kind by kind (service behaviour as implemented)

| Kind | Produced by | `retryable` | `next_action` | Automatic behaviour | Evidence |
|---|---|---|---|---|---|
| `NETWORK_OFFLINE` | connect/timeout/body errors, truncated bodies | true | `retry` | ≤3 retries with backoff, then failed | H04, V12 (backend); service end-to-end |
| `AUTH_REQUIRED` | HTTP 401, 407 | false | `sign_in` | none | **E01** (process), S01 |
| `LINK_REFRESH_REQUIRED` | HTTP 403 (*heuristic*), 404, 410 | false | `refresh_link` | none | **E01**, S01 |
| `REMOTE_CHANGED` | 412, ETag/length change on resume, redirect while resuming, changed files at finalization | false | `choose_restart_or_keep` | none (a 200 with a new identity restarts cleanly without an error, V03/K04) | **E04**, V04, V07, K04 |
| `RANGE_UNSUPPORTED` | aria2 only (error code 8) | false | `choose_restart_or_keep` | none | `errors::tests` (aria2) |
| `INVALID_RANGE` | wrong `Content-Range`, 416, 206 to a full request, wrong final length | false | `choose_restart_or_keep` (backend); `none` (finalization length check) | none | V08, V10, S01 |
| `CHECKSUM_MISMATCH` | trusted SHA-256 differs at finalization (the staging file is deleted) | false | `none` | none | F03 |
| `DISK_FULL` | `ENOSPC`/quota, budget refusal | true while waiting | `free_disk_space` | waits with `disk_unavailable`, continues by itself; aria2: terminal | DK01–DK07 (now also assert `next_action`) |

| `HOST_NOT_INSTALLED` | not produced by the service (reserved for the browser fallback, BRW-04) | — | `install_desktop_app` | — | catalogue only |
| `SCAN_BLOCKED` | not produced (no scanning yet, ADV06) | — | `none` | — | catalogue only |
| `BACKEND_CAPABILITY_UNAVAILABLE` | capability gate (scheme, proxy, …); resume refused without a strong validator | false | `none`; **resume refusal: `choose_restart_or_keep`** | none; the job stays paused with its partial data | **E03**, D04/D05, X05 |
| `SERVER_BUSY` | 408, 429, 5xx | true | `wait` | ≤3 retries, `Retry-After` honoured, `rate_limit_cooldown` blocker | S02, service end-to-end (503 + Retry-After) |
| `TLS_HANDSHAKE_FAILED` | untrusted/expired/mismatched certificate, handshake alert | false | `none` | none | T02–T04, service end-to-end |
| `SERVICE_UNAVAILABLE` | client cannot reach the service; jobs interrupted without a usable checkpoint | true (client); false (interrupted job) | `retry` (client); `none` (interrupted) | none | CLI tests, B1.1 kill test |
| `INVALID_REQUEST` | unknown job, bad params, terminal-job commands, redirect loop, encoded body, unexpected status | false | `none` | none | core tests, H06, D05 |
| `IDEMPOTENCY_CONFLICT` | same key, different request | false | `none` | none | core tests |
| `INTERNAL` | unexpected local failures (`retry` when a new job could not be recorded) | false | `contact_support` (`retry` for the record failure) | none | core tests |

*Heuristic* means the classification guesses a cause the server does not state:
- a 403 may mean an expired link, a revoked link or a missing sign-in, so the text names all three;
- `NotFound` on the destination is read as a missing volume or folder.

All other rows are produced from an explicit status or condition and are verified by the cited fixture.

### Defects found and fixed

1. **Resume refusal without a strong validator** reached clients with `next_action: none`. The service-level refusal
   already used `choose_restart_or_keep`, but the backend's per-job refusal did not.
   - Fix: `resume_refusal` maps `BACKEND_CAPABILITY_UNAVAILABLE` from `backend.resume` to the restart choice, both on
     an immediate resume and at admission.
   - Found by E03; unit test `a_refused_resume_offers_the_restart_choice_only_for_capability_refusals`.
2. **An occupied final name** (another program created the file after the name was frozen) was reported as
   `INVALID_REQUEST`, which describes the client, not the folder.
   - It is now `DESTINATION_UNWRITABLE` and still not retryable.
   - The detail is unchanged ("Downova did not overwrite it …"), and F04 asserts the new kind.
3. **CLI hints promised missing or wrong steps:**
   - "free disk space, then resume": a waiting job continues by itself, and resuming changes nothing;
   - "export diagnostics": no diagnostics export exists;
   - "sign in on the website, then add the link again": Downova cannot use sign-ins or cookies, so this did not help.

### Copy

- **Desktop UI** (`apps/desktop/src/i18n/messages.ts`, English and Bangla):
  - `error.kind.<KIND>` for all 19 kinds;
  - `error.action.<action>` for the 9 actions other than `none`;
  - three follow-ups: stopped (add the link again to start over), continues by itself, tries again automatically.
  - `present.ts` `errorText(download, t)` picks the text from `kind`, `next_action`, `phase`, `desired_state` and
    `blockers` only. The table's description cell shows the localized summary instead of the English detail. The
    layout is unchanged; the full action and follow-up are for the B2 details view.
- **CLI** (`crates/cli/src/output.rs`, English only):
  - `explain(kind)` prints a `meaning:` line (`Meaning` in `dm get`).
  - `hint(action, situation)` depends on where the error is seen: a refused command, a download that is still waiting,
    or a failed download (which never resumes; adding the link again starts over).
  - JSON output and exit codes are unchanged; a test asserts that the JSON has no new field.
- **What the copy does not promise:** authenticated downloads (the sign-in text says Downova cannot sign in or use
  cookies yet), diagnostic exports, automatic renaming, or resuming a failed download.

## 4. B1 acceptance gaps

### CORE-04 — repeated kills (process kills only)

- **R01:** a single-connection job and a segmented job; N hard kills, each right after a newer committed checkpoint of
  the single-connection job; every cycle checks that whatever is reported completed is byte-exact.
- **R02:** a crash at each of the 5 finalization boundaries, repeated N times with fresh data each time; every restart
  ends with exactly one correct file and one download of the source.
- N comes from `DOWNOVA_KILL_REPS` (default 3 in plain `cargo test`).

| Run | Result |
|---|---|
| N = 3 (default) | R01: 3/3 kills mid-transfer; R02: 15 crashes; both SHA-256 exact |
| N = 10 | R01: 10/10 kills mid-transfer, 16 recoveries, both SHA-256 exact; R02: 50 crashes, all exact (73 s) |
| N = 20 | R01: 20/20 kills mid-transfer, 33 recoveries, both SHA-256 exact; R02: 100 crashes, all exact (179 s) |

### CORE-04 — forcibly terminating the desktop

Packaged smoke step **E** (`scripts/smoke/packaged-smoke.mjs`):
1. A fresh desktop starts its own `dm-service`.
2. A slow transfer begins.
3. The desktop process alone is killed (Windows `taskkill /F` without `/T`; Unix `SIGKILL`). The service is that
   process's child.
4. The service must keep running, and the file must complete with the exact SHA-256.

The local Windows run passed every step:
- E1: the desktop started service pid 21480;
- E2: the desktop was killed at 2,359,296 of 6,291,456 bytes while transferring;
- E3: the service was still alive;
- E4: the download completed with SHA-256 `c27503fe…9181`, matching the fixture.

The existing graceful-close step C also passed in the same run.

### COR-08 — WAL + `synchronous=FULL` benchmark

- **Test:** `crates/storage/tests/checkpoint_latency.rs`, `#[ignore]`d.
- **What it measures:** `Store::save_checkpoint` with the production settings (WAL, `synchronous=FULL`, exclusive
  locking). Each commit is one job-row update plus one checkpoint upsert, on isolated temporary databases, with
  checkpoint payloads of 512 B, 4 KiB and 64 KiB.
- **Comparison only:** the same two statements on a raw connection with `synchronous=NORMAL`. Production never uses
  that mode.
- **After each run:** the test reopens the database and checks that the last commit is there.

Local run: 1000 commits per row, release build, temp folder on the NVMe SSD (NTFS), Windows Defender active (not
excluded).

| Configuration | mean | p50 | p90 | p99 | max |
|---|---|---|---|---|---|
| FULL (production), 512 B | 4.339 ms | 3.712 | 4.159 | 7.829 | 159.589 |
| FULL (production), 4 KiB | 3.912 ms | 3.790 | 4.143 | 7.226 | 9.818 |
| FULL (production), 64 KiB | 4.029 ms | 3.864 | 4.334 | 8.428 | 13.292 |
| NORMAL (comparison), 512 B | 0.460 ms | 0.039 | 0.067 | 0.134 | 382.875 |
| NORMAL (comparison), 4 KiB | 0.178 ms | 0.043 | 0.073 | 0.276 | 42.104 |
| NORMAL (comparison), 64 KiB | 0.887 ms | 0.150 | 0.263 | 32.659 | 80.224 |

- **A first run (200 commits per row)** gave FULL p50 3.7–4.0 ms and p99 7.4–10.8 ms.
- **Cost at the production cadence:** the service commits a checkpoint at most every 2 s per transferring job, plus at
  pause and shutdown. With 3 active files that is about 1.5 commits/s, around 6 ms of synchronous I/O per second (well
  under 1 % of wall time).
- **Decision:** keep `synchronous=FULL`, unchanged. Single-machine, single-OS figures; not a cross-platform claim.
- **What the modes guarantee:**
  - A process kill cannot lose a committed transaction in WAL with either setting; the kill tests (K01, R01) show
    that the service never claims more than the data on disk.
  - `FULL` additionally syncs the WAL at every commit, which is what a power loss needs.
  - **No power-loss test was run.** No durability beyond process kills is claimed.

## Limitations and unverified cases

- **Kill evidence:** process kills only, no power-loss test. The service and the `http` engine are one process, so
  "engine kill" equals service kill. aria2 kill was covered in B1.1 (interrupted, no orphan).
- **Leftover partial files:** a job that fails before receiving any byte (401/403/404/410) leaves an empty
  `<staging>.downova-part`. This is existing behaviour, asserted as such in E01, and is a cleanup candidate for B2.
- **E06 coverage:**
  - Windows uses an ACL deny for Everyone; Unix uses mode 0555. Neither has run on macOS or Linux yet.
  - As root, the Unix restriction is ignored and the test reports "not run".
  - Read-only volumes and network shares are classified by code (`refused_destinations_are_classified`) but not
    process-tested.
- **Heuristics:** a 403 is not distinguishable from a missing sign-in or a revoked link, and `NotFound` is read as a
  missing volume or folder.
- **Reserved kinds:** `HOST_NOT_INSTALLED` and `SCAN_BLOCKED` have copy but are never produced by the service yet.
- **Bangla copy:** written for the UI, not reviewed by a native-speaker QA pass (that is planned for the B3 Bangla QA
  milestone). The CLI is English only.
- **`downloads.v1.retry` and `replaceSource`:** these API methods are not implemented. A failed download is started
  again only by adding its link again, and the copy says exactly that.
