# Installed-app acceptance runbook (B2.32, corrected in B2.33)

- **Purpose:** the installed-app and human checks that B2 still needs, as one executable procedure. Automated
  checks (packaged smoke, the concurrency acceptance script) never stand in for these rows; where an automated row
  covers part of a check, it is named next to the row.
- **Who:** a tester with a **clean VM or a separate OS account** on each target OS (Windows 11 x64, macOS arm64,
  Ubuntu 22.04/24.04 x64). Never the developer's everyday account: installing registers the browser helper for that
  user (Windows: `HKCU\Software\Google\Chrome\NativeMessagingHosts\com.downova.host` and
  `HKCU\Software\Microsoft\Edge\NativeMessagingHosts\com.downova.host`, pointing at a manifest under
  `%LOCALAPPDATA%\Downova\native-messaging\`), and the app takes a per-user single-instance lock.
- **Build:** the **normal** package (not the smoke-test package), recorded by SHA-256 in PROGRESS.md and the current
  report. Verify the hash before installing: `Get-FileHash <file> -Algorithm SHA256` on Windows,
  `shasum -a 256 <file>` on macOS, `sha256sum <file>` on Linux. Check that `build-info.json` says
  `"smoke_feature": false`.
- **Recording:** each row gets PASSED, FAILED or NOT RUN, the build hash, the OS and browser version, and the
  observer: **human** (a person looked), **agent** (an AI agent drove and read the screen) or **automation** (a
  script asserted it). Evidence is a screenshot, the fixture log, `dm --json` output or a hash. **Page zoom**
  (Ctrl/⌘ +, which smoke P2 also uses) and **OS display scaling** (Windows Settings → Display → Scale; macOS
  Displays; GNOME Settings → Displays → Scale) are different checks: record which one was used.

## 0. Setup (each OS)

1. **Fixture, on the test machine itself:** `node scripts/acceptance/fixture-server.mjs --port 8765`. It binds
   `127.0.0.1` only, so it must run on the machine under test. It prints every SHA-256 and serves the scenarios at
   `http://127.0.0.1:8765/`. Open that page in Chrome and Edge.
2. **Large files for the concurrency rows:**
   `node scripts/perf/fixture-process.mjs --count 7 --size-mib 256 --port 8766`. Its first line is JSON with
   `base` (`http://127.0.0.1:8766`) and each file's SHA-256. The URLs are `<base>/f0.bin?slow=100` …
   `<base>/f6.bin?slow=100`: about 0.6 MB/s per request, so a 256 MiB file takes minutes even when the host's 8
   requests are shared. `<base>/__stats` shows the requests and bytes the server handed out.
3. **Install** (as the test user):
   - Windows: `Downova_0.1.0_x64-setup.exe` (per-user NSIS; its install hook registers the helper for Chrome and
     Edge). The `.msi` has no install or uninstall hook: the app registers the helper on first launch.
   - macOS: open the `.dmg`, move Downova to Applications, open it once (the first launch registers the helper).
   - Linux: `sudo apt install ./downova_0.1.0_amd64.deb`, then open Downova once as the desktop user. The AppImage
     refuses to register the helper while it runs from its mount; use the `.deb` for every browser row.
4. **Extension:** Chrome/Edge → Extensions → Developer mode → Load unpacked → `extension-unpacked/` from the package
   folder. Its manifest key gives the ID the helper allows. Check the popup says "Service ready".

## 1. Installed concurrency

Downloads in this section use the Main queue. `dm` is in the install folder (Windows
`%LOCALAPPDATA%\Downova\`, macOS `/Applications/Downova.app/Contents/MacOS/`, Linux `/usr/bin/`).

| ID | Steps | Expected |
|---|---|---|
| C1 | Options → Simultaneous downloads | "What this allows" shows the saved limit 3, Main 3, "Main can run at once 3", "Active now 0" |
| C2 | Set the limit to 6 and save; press **Change queue limit**; set Main to 6 → Set limit → close Manage queues | Back in Options: Main 6, "Main can run at once 6". `dm concurrency` → 6; `dm queues` → main `max_active` 6 |
| C3 | Add `f0`–`f5` (Add URL, or `dm add <URL>` six times) | All six rows show a rising percentage before any completes; `dm list` bytes rise for all six. Record each file's SHA-256 after completion (C11) |
| C4 | **Non-preemptive decrease.** While the six run, set the global limit to 2 and save. Add `f6` | No running download stops: all six keep gaining bytes for 30 s. "Active now 6" with the note "More downloads are active than the limit…". `f6` waits: `dm get <JOB-ID>` shows phase `queued` with blocker `queue_limit` |
| C5 | **Admission only when capacity exists.** Set the global limit **and** Main to 7 | `f6` starts within a few seconds: 7 active, within both limits. (Raising the limits back to 6 would not start it, because six are running.) |
| C6 | Pause one download (Stop on the toolbar, or `dm pause <JOB-ID>`) | It stays paused (no bytes for 30 s); the others continue |
| C7 | Downloads → Stop queue on Main (or `dm queue-stop main`); wait 30 s; then Start queue (`dm queue-start main`) | While stopped: every unfinished Main download stops gaining bytes and shows the queue-stopped reason (blocker `queue_stopped`); the one paused in C6 stays paused. After Start: they continue within the limits; the C6 download stays paused (starting a queue never resumes a manual pause, ADR 0017) |
| C8 | Cancel one running download (or `dm cancel <JOB-ID>`) | It ends `cancelled`; no final file under its name; the others continue |
| C9 | **Exit and stop.** Tray → Exit and stop downloads → confirm | The window and the service end (no `dm-service` process). Every unfinished download is **paused durably** (ADR 0012) |
| C10 | Open Downova again | The global limit and Main's limit are still 7 and 7. **Nothing starts by itself**: the downloads from C9 show paused at their last progress. Select each and press Resume (or `dm resume <JOB-ID>`): each continues from its progress (`<base>/__stats` shows ranged requests starting past 0), not from zero |
| C11 | Wait for completion | Every completed file matches its SHA-256 from the fixture's first line; the cancelled one has no file |

## 3. Browser fallback and uninstall

| ID | Steps | Expected | Automated counterpart |
|---|---|---|---|
| F1 | Tray → Exit and stop downloads. Then right-click a fixture link → Download with Downova, and click `public.bin` with capture on | The helper **never starts the service** (`crates/browser-host/src/handler.rs`, `NOT_RUNNING`), so a stopped service is a deterministic "unavailable". The popup says Downova is unavailable and to open the app; with capture on, the browser keeps and completes the download; no job appears after reopening Downova | smoke R3 X4 (no service for the helper) |
| F2 | `dm-browser-host status --browser chrome --browser edge`, then `dm-browser-host unregister --browser chrome --browser edge`, then right-click a fixture link | `status` lists both as owned; after `unregister` the popup says the helper is not installed and the browser keeps the download. `dm-browser-host repair --browser chrome --browser edge` restores it ("Service ready" again) | smoke R5 (repair, ownership) |
| F3 | Helper never answers; acknowledgement lost after acceptance; acknowledgement for a different request; retry with the same key | Covered by automation only: a normal install offers no way to cause these faults (they need a fault-injecting helper). Record the smoke rows here | smoke R3 **X1–X6** (B2.33) |
| U1 | Before uninstalling, add an unrelated manifest beside Downova's (any `com.example.test.json`; on Windows also a `HKCU\Software\Google\Chrome\NativeMessagingHosts\com.example.test` value). Uninstall: Windows Settings → Apps → Downova (NSIS: its hook unregisters the helper; after an MSI install run `dm-browser-host unregister --browser chrome --browser edge` first). macOS: `dm-browser-host unregister --browser chrome --browser edge`, then move the app to the Trash. Linux: the same `unregister` as the desktop user, then `sudo apt remove downova` | Downloaded files and the download folder stay. Only entries naming this installation's helper are removed; the unrelated manifest and value remain | smoke R5 (unrelated entry kept) |
