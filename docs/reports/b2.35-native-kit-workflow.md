## 1. What was missing

- **No normal packages for macOS or Linux.** Package smoke builds only `--smoke` packages (test-only feature compiled
  in), on every push, and uploads them as `…-smoke-test-…` artifacts. Those are never acceptance candidates, so no
  tester could obtain a normal macOS or Linux package.
- **`build-kit.mjs` assumed Windows:**
  - `--zip` used `tar -a`, which GNU tar on Linux cannot do (and which breaks when Git Bash's tar comes first on
    Windows);
  - the "primary installer" was the NSIS `setup.exe`;
  - the quick-start said "no macOS or Linux package", wrongly for those kits;
  - the extension check only required a manifest key, not the ID the helper allows.

## 2. What changed

- **`.github/workflows/acceptance-kit.yml`** (new):
  - **Trigger:** `workflow_dispatch` only, so documentation pushes never rebuild packages.
  - **Permissions:** `contents: read`. No secrets, signing credentials or release steps.
  - **Runners:** native `windows-latest` (windows-x86_64), `macos-latest` (macos-aarch64) and `ubuntu-22.04`
    (linux-x86_64; the glibc baseline is kept).
  - **Setup:** the same pinned setup as package smoke (pnpm from `packageManager`, Node 24, `rust-toolchain.toml`,
    rust-cache, `pnpm install --frozen-lockfile`).
  - **Steps:**
    1. `node scripts/package.mjs`: **normal**, no `--smoke`;
    2. `build-kit.mjs --zip`, with the **source check on** (no `--skip-source-check`);
    3. `validate-kit-zip.mjs` on the delivered ZIP.
  - **Logs and evidence** go to `$RUNNER_TEMP`, never into the checkout: `package.mjs` records `git status` and
    `build-kit` refuses a package built with uncommitted paths.
  - **Artifacts:**
    - `downova-acceptance-kit-<label>-<sha>`: the kit ZIP, `.zip.sha256`, `.zip.json`, and the evidence
      (build-info, package and extension SHA256SUMS, `kit-validation.json`). Uploaded **only when validation
      passed**.
    - `downova-acceptance-kit-<label>-<sha>-logs`: the build, kit and validation logs plus the evidence, uploaded
      **always**, so failures keep their logs.
    - Both are kept 30 days and are never attached to a release.
  - **Job summary:** separate rows for package build, kit build, kit validation (build and delivery only), and
    installed-app and human acceptance, which always reads `NOT RUN`.
  - **Signing:** whatever `package.mjs` records (`unsigned` on Windows and Linux; macOS `ad-hoc (codesign -), not
    notarised`), visible in `build-info.json` and in the quick-start header.
- **`scripts/lib/zip.mjs`** (new), a ZIP writer and reader using Node built-ins only:
  - deflate or store, CRC-32;
  - Unix permissions (AppImage and `verify-kit.mjs` stay 0755, the rest 0644);
  - a fixed timestamp;
  - refuses unsafe or duplicate names and anything over 4 GiB (no ZIP64).
- **`scripts/acceptance/build-kit.mjs`:**
  - archives with `zip.mjs` and writes `<zip>.sha256` and `<zip>.json` (bytes, SHA-256, label, source commit);
  - **derives the Chrome extension ID from the manifest key and requires it to equal `DEV_EXTENSION_ID`**
    (`crates/browser-host/src/lib.rs`);
  - per-OS primary installer (NSIS setup, `.dmg`, `.deb`);
  - a generated quick-start header naming this kit's platform, files, hashes, signing and source;
  - an allowlist of kit paths (no caches, `node_modules`, `.git` or `target`).
- **`scripts/acceptance/validate-kit-zip.mjs`** (new), checking the delivered ZIP:
  1. reads the archive (CRCs; one top folder; exactly the files `SHA256SUMS.txt` lists);
  2. extracts it with the OS's standard tool into a fresh temp folder (bsdtar on Windows, `ditto` on macOS,
     `unzip` on Linux) and checks executable bits on Unix;
  3. runs `verify-kit.mjs`;
  4. starts both fixtures with the checklist's commands (S2, S3), downloads `f0.bin` and `public.bin` and compares
     them with the announced SHA-256;
  5. stops and reaps only its own two processes;
  6. writes `kit-validation.json` and a job-summary section, and exits 1 on any failure.
- **Tester documents:**
  - `docs/acceptance/b2-quickstart-bn.md`:
    - how to find the workflow run, choose the platform artifact, check the kit ZIP's hash and extract it;
    - page zoom versus OS display scaling;
    - macOS (stays in `/Applications`, ad-hoc signed) and Linux (`.deb` for every browser row; the AppImage does not
      register the helper);
    - that a download or checksum is not acceptance.
  - `b2-checklist.md` S4 no longer hard-codes file names.

## 4. Not run

- **The native matrix of `acceptance-kit.yml`.** It runs only after these changes are pushed and a maintainer
  starts it (Actions → "Acceptance kit (normal packages, internal)" → Run workflow). Until then **no macOS or
  Linux kit exists**, and no native-runner result is claimed.
- **macOS and Linux extraction** (`ditto`, `unzip`) and their permission checks: covered by the workflow when it runs.
  The Linux `unzip` test in `zip.test.mjs` is skipped on Windows.
- **Every installed-app and human row:** no clean VM or test account here. An artifact download or a passing kit
  validation is not acceptance.
