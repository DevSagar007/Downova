## 1. What changed and why

### macOS Clippy (CI #45)
**Root cause (confirmed by code inspection):**
- `SystemNotifier` stored `app_id` on every OS.
- Only the Windows toast path read it.
- The `allow(dead_code)` covered neither Windows nor macOS, so on macOS the field was dead and `-D warnings` failed.

**Fix:** the field exists only on Windows (`#[cfg(windows)]`).
- **macOS:** still registers the bundle with `set_application`, once and process-wide, in the constructor.
- **Linux:** acknowledges the unused argument explicitly.
- **Lints:** no lint was disabled.

**Verified locally:**
- Windows: Clippy with and without the `notify` feature.
- Linux: a cross-check of `dm-platform --features notify --target x86_64-unknown-linux-gnu`.
- macOS: cross-checking was UNAVAILABLE, because `mac-notification-sys`'s build script needs an Apple C toolchain.

**Initialization review:**
- `set_application` can fail (bundle unknown, or already set); its error only means the default sender is used.
- Delivery failures are reported through `last_delivery_failed`.
- No other platform defect was found in the code.

### Notification delivery
Each notice used to be one `spawn_blocking` task. That had two consequences:
- Notices could reach the system out of order, and `last_delivery_failed` described whichever task finished last.
- A desktop notification service that stopped answering accumulated blocked tasks.

`notify::Delivery` now hands notices to the system in decision order on one thread, through a bounded queue of 32.
Overflow drops the notice and reports a failed delivery; downloads are unaffected.

**Unchanged:** the semantics (off by default; durable outcomes only; at most once; no catch-up; en/bn; no
links/paths). Test: `delivery_is_ordered_bounded_and_never_blocks_the_caller`.

### IPC framing and large lists
Before, `read_line_from` reported an over-long line and a peer that stopped mid-line as the same `InvalidData`
error, and every client turned it into "service unavailable". For an oversized list (more than 64 MiB, roughly
100,000 jobs), that produced an **endless loop**:
1. The subscription failed as "unavailable".
2. The window lost its connection.
3. An attach-only probe succeeded, because `hello` is small.
4. The window subscribed again, back to step 1.

**Now:**
- An over-long line is the typed `CallError::TooLarge`. Every client maps it:
  - CLI: exit "unexpected";
  - browser host: "uncertain";
  - desktop: a non-retryable rejection, or "uncertain" for a mutation.
- A peer that stops inside a line is a lost connection.
- The window falls back to polling only when the subscription is refused as unknown (`INVALID_REQUEST`). Any other
  refusal ends in a reported **"The download list could not be loaded"** state (en/bn) with Reconnect. Nothing
  repeats automatically.
- Stream restarts in a row without an applied event are immediate three times, then back off from 500 ms to 8 s.

**Limits unchanged:** 1 MiB for requests and 64 MiB for responses and events. The 10,000-record behaviour is unchanged
(P1, history_10k).

### Event batching and ordering
Review found no ordering defect in `ServiceProvider`:
- queued events are applied before every acknowledgement;
- a snapshot drops the queued batch;
- removed IDs are filtered at every entry point;
- timers, listeners and subscriptions are released on teardown.

Tests now prove each case (`src/services/event-ordering.test.tsx`, 15 tests), and each relevant test failed with its
guard removed.

**One limit remains:** the stream and the acknowledgement travel on different connections, so an event emitted
*before* a mutation can arrive *after* its acknowledgement. The state is then briefly stale, until the mutation's own
event, which the service always sends next and which normally falls in the same 50 ms batch. A strict guarantee would
need a per-job revision in the contract. That is not done: it would be a protocol change without a demonstrated user
impact.

### Virtualized list: three defects fixed
1. **Removal picked the wrong neighbour.** "Remove from list" chose the next row *rendered in the DOM*. A selected row
   scrolled out of view is rendered alone (pinned), so removing it selected a far-away row. The window now takes the
   neighbour from the table's full visual order (`orderRef`), and selecting it pins and focuses it.
2. **Focus could fall to the page.** A focused row removed elsewhere (`dm remove`, clean-up, another window) dropped
   focus to the page. It now moves to the row at the same position.

Both new tests failed without the fixes.

3. **A blank band at 200 % zoom (found in the packaged window).** The first P2 run passed its checks, but an
   ad-hoc probe of the same package then measured, scrolled to the middle of 2,000 rows at CSS zoom 200 %, only 4
   visible rows and a 169 px blank band at the bottom of the list.
   - **Cause:** the row and header heights were read with `getBoundingClientRect()` (zoomed pixels), while
     `scrollTop` and `clientHeight` are layout pixels. The rendered window was computed for half the true scroll
     position.
   - **Fix:** the heights are divided by the scroller's own zoom factor. They stay fractional, so 10,000 rows
     accumulate no rounding error.
   - **Check:** P2 now also asserts that the rendered rows cover the list viewport, at the top and the middle, at
     every zoom and theme.
   - **Scope:** browser page zoom and OS scaling keep both units consistent, so this mainly affects CSS zoom and
     transforms. The probe uses CSS zoom as a stand-in for OS zoom, so the fix makes the list independent of which
     one is in effect.

**Also added:**
- tests for selection through sorting and filtering, hidden spacers and continuous `aria-rowindex`;
- in the real packaged window (smoke P2): page zoom 100/150/200 % in light and dark, and a Bangla search over the
  whole dataset.

### Measurement tooling
`scripts/perf/measure.mjs` now records three startup times on one clock from the desktop spawn:
- service ready;
- WebView first contentful paint;
- list ready (marked as an upper bound when it was earlier than the DevTools attach).

**New scenarios:**

- `scripts/perf/compare.mjs` aggregates alternating runs with sample counts.

## 3. Resource measurements (Windows only)

**Method:**
- **Packages:** two equivalent normal release packages, measured on the same machine on the same day, in
  alternating runs (old, new, old, new…) with rotated scenario order.
  - **before:** `b223`, the B2.21–B2.23 internal build;
  - **after:** `b224`, this batch's final internal build. Its product code is identical to
    `dist-packages/windows-x86_64` (§5).
- **Isolation:** isolated profiles; the full owned process tree (desktop, 6 WebView2 processes, service).
- **Runs:** 5 per scenario, and 10 for one and three transfers.
- **CPU:** the share of the whole machine (12 logical cores) over a 10 s window. Machine: AMD Ryzen 5 5600G with integrated Radeon graphics, 12 logical cores, 7.4 GiB.
- **Commands:**
  - `node scripts/perf/measure.mjs --package-dir dist-packages/<p>-windows-x86_64 --runs 1 --rotate <r> --out
    perf-results/cmp-<p>/r<n>`, alternating;
  - `node scripts/perf/compare.mjs perf-results/cmp-b223 perf-results/cmp-b224`.
- **Raw results:**
  - `perf-results/cmp-b223/`, `perf-results/cmp-b224/`;
  - `perf-results/cmp-summary.json`;
  - `perf-results/cmp-modes.txt` (the per-mode split);
  - diagnostics in `perf-results/diag-baseline/` and `perf-results/diag-after/`;
  - process types in `perf-results/proc-types/`;
  - the experiment in `perf-results/exp-disable-gpu/`.
- **Versions:** WebView2 156.0.4314.58 for every run.

**How to read this table:** the medians move in both directions by up to 46 MiB, but the cause is not the build.
The WebView2 **GPU process** settles, per launch, at either about 51–54 MiB or about 96–109 MiB:
- `proc-types`: 6 launches of the same build gave 54/51/100/51/54/54; the renderer stayed at 32–36 MiB.
- **Within each mode the builds agree within about 3 MiB** (`cmp-modes.txt`). Examples:
  - one transfer, low mode: 177.5 vs 180.1 MiB;
  - 1,000 records, high mode: 221.8 vs 221.6 MiB.

- **The high mode came up 21 times in 50 runs before and 27 times in 50 after.** With these counts that is not a
  build difference.

**Conclusions:**
- **No resource regression and no resource improvement is claimed for this batch.**
- The B2.21–B2.23 "178 → 197 MiB" was this effect with n = 5: in those runs, 3 of 5 "before" launches and 1 of 5
  "after" launches landed in the low mode.

**Startup:**
- **Not migrations:** the service starts in under about 0.1 s, even on a new profile. The multi-second outliers
  happen between the desktop spawn and the service answering, in both builds, and are **not explained**.
- **Candidates, not established:**
  - WebView2 profile creation for a new user-data folder;
  - antivirus scanning of freshly extracted executables;
  - machine load.

**Cycles:**
- After 5 hide/reopen cycles and 3 service restarts, the JS heap after GC is about 0.6 MiB higher in both builds,
  and listeners grow by 3.
- With one cycle set per run, this cannot tell a slow leak from warm-up (compiled code, caches). A longer cycle
  series is listed as follow-up work, not claimed either way.

### Diagnostics (separate instrumented runs, n = 5 each; never mixed into the table above)

During active transfers, both builds show the same profile:
- JS heap used 2.3–3.5 MiB, about 2.3 MiB after GC;
- about 28 DOM mutation callbacks and about 360 layouts per 10 s, matching the service's 400 ms progress
  coalescing;
- under 0.1 s of script time per 10 s.

Event listeners rise to 1,000–1,600 between GCs and return to about 176 after a forced GC: this is garbage, not
retention. **The React side therefore does not explain any process-level difference.**

### Experiment, not a change: WebView2 without GPU acceleration

`--webview-args --disable-gpu` was tried on the new package only, 5 runs each:
- **GPU process:** about 15 MiB, and the bimodality disappears.
- **Memory:**
  - idle 115 MiB [115–117];
  - one transfer 129 MiB [128–135];
  - 10,000 records 192 MiB [189–193].
- **Unchanged on this machine:** CPU (0.17 % / 0.69 %), and search/scroll latency (33 ms, frame-bound).

**Not adopted:**
- It is a rendering-stack decision for all Windows users.
- Its effect on other GPUs, high-DPI displays, battery and long sessions is unmeasured.
- It needs an ADR and a wider evaluation (next batch).
