## 2. Root causes and fixes

| Failure | Cause | Category | Fix |
|---|---|---|---|
| detect test on macOS and Ubuntu 24.04 (actual `[]`, expected `[Native]`) | The simulated Windows locations were single strings with `\` separators (`r"Mozilla Firefox\firefox.exe"`). On macOS and Linux a backslash is a file-name character, so `join` looked for one file with that literal name. The fixture created real nested folders. On Windows `\` is the separator, so it passed there | product code (path construction); the fixture was correct | `windows_locations()` returns path components, joined with the host's separator. Real Windows paths are unchanged. New test `windows_locations_are_separator_free_components_found_on_every_host`: every family, every program directory; a folder with the executable's name is not an installation |
| a07 on Ubuntu 22.04 (no validated resume request) | A fixed 300 ms sleep before pausing. On a slow runner the TLS handshake and first chunks took longer, so the pause came before any resumable progress and the resume was a fresh GET without `If-Range`. (Pausing after completion was the other possible case.) | test timing (fixture coordination); no engine defect | Wait, bounded at 20 s, for a **durable checkpoint** with non-zero confirmed bytes. Pause, and assert the transfer is paused before completion. Every request after resume must have a non-zero `Range` start, `If-Range` and the session cookie. Exact length and SHA-256. The fixture is slower (20 ms per 16 KiB) so completion is about 5 s away |
| Linux smoke H2, H3, K7 (paused job `failed` after a restart; Resume stays failed) | The links have a query (`?slow=…&step=h`), which the service treats as protected and seals with the data key from the OS credential store (ADR 0027). The Linux smoke job had a D-Bus session but **no Secret Service**. The release service therefore had no data key, kept the protected part in memory only, and after the restart correctly reported `LINK_REFRESH_REQUIRED` (pause kept). Windows and macOS have real stores and passed | runner setup | `scripts/smoke/linux-secret-service.sh` starts gnome-keyring's secrets component inside the job's own D-Bus session (random per-run password). It proves the store with a store, lookup and clear round trip before the smoke runs, and fails explicitly if it is not usable. No smoke expectation was changed. No debug vault is used in release packages |

**Deterministic coverage of both credential-store cases** (service unit tests):
- `with_a_store_a_paused_protected_link_survives_a_restart_and_resumes`: with a working store, the paused job comes
  back paused with its 262144 bytes and transfers nothing on its own. Resume restores the unchanged sealed
  checkpoint with the full link. No secret is on disk.
- `without_a_store_a_paused_protected_link_needs_a_refresh_and_never_resumes_blind`: the manual pause is kept,
  with `LINK_REFRESH_REQUIRED` and next action Refresh link. Resume starts no transfer. No secret is on disk.

| macOS verify, revealed by `--no-fail-fast` on `7618eaa` | `update::tests::the_target_names_this_package_format_only`: Tauri's `bundle_type()` reports `App` for **every** macOS binary, so a development or test binary counted as an installed `.app` | product code | Only an executable inside `<name>.app/Contents/MacOS/` is an app bundle (`inside_app_bundle`, tested on every host). Commit `69a9068` |
| ubuntu-24.04 real-browser S4 on `69a9068` (`kept_bytes 0`, no candidates, `failed`) | The CI hand-off step ran the debug service without an OS credential store (no Secret Service in that job). With no data key, the signed-in link and checkpoint were never sealed. After the hard restart, the restore path for a credential job without a sealed link correctly failed it with `AUTH_REQUIRED`, so it was never a reconnect candidate. **Reproduced locally:** with the store off (`DOWNOVA_VAULT=off`), the same result (`failed`, `AUTH_REQUIRED`, no candidates, checkpoint `sealed: 0`). With the real Windows store S4 passed | runner setup; S4 also had timing assumptions (fixture coordination) | (1) `ci.yml`: the ubuntu-24.04 hand-off runs as `dbus-run-session -- bash scripts/smoke/linux-secret-service.sh node scripts/e2e/chrome-handoff.mjs`, with `dbus gnome-keyring libsecret-tools` declared. The Windows and macOS steps are unchanged. (2) The wrapper keeps the keyring files in a task-owned temporary folder, removes it afterwards, and runs the command instead of `exec` so the cleanup happens. (3) S4: see below. Commit `3ae2732` (local; see §3) |

**S4 now proves the authenticated resume path** (`scripts/e2e/chrome-handoff.mjs`, `scripts/e2e/signed-in.mjs`):
- **No fixed sleeps.** The fixture holds the body at a gate (3 MiB of 8), so the download cannot complete before the
  restart.
- **Durable progress proven before the restart:** once the service has received the bytes up to the gate, it is
  killed hard. With the service gone (it holds its database exclusively while running), the committed checkpoint
  is read: `confirmed_bytes > 0` and `sealed = 1`, which proves the data key was in the OS store.
- **No blind transfer:** nothing is requested before the explicit reconnect, and the job waits with
  `sign_in_required` / `AUTH_REQUIRED`.
- **Same job, same bytes:** it is offered as the only candidate, the user explicitly chooses it, and a fresh
  session reconnects it. The restored bytes equal the proven checkpoint, and the first request starts exactly
  there (`bytes=<kept>-…`) with only the fresh cookie.
- **Result:** SHA-256 exact, and neither secret is in the data folder or the extension's session storage.
- **Not proof of resume:** a fresh download from 0 fails S4.
- **The temporary sign-in is still lost on restart.** Only the data key is persistent.

**Verification visibility:** `pnpm verify` now runs `cargo test --no-fail-fast`. Any failure still fails the step,
but every test binary runs, so one CI round shows all failures.

## 5. Follow-up: S4 assertion for segmented resume (2026-11-08)

- **What failed:** the PR runs on `be09937` ([42461330384](https://github.com/DevSagar007/Downova/actions/runs/42461330384)) failed S4 on Windows, macOS and ubuntu-24.04.
- **The real behaviour was correct.** The Linux Secret Service worked: the checkpoint was sealed (1,900,544 bytes), the download waited for a sign-in, it was reconnected, and the SHA-256 matched.
- **Cause: a test assertion added in B3.7 was wrong for segmented downloads.** It required the first range after the reconnect to start at the total kept bytes. With several segments, each continues from its own offset, so the first range was `bytes=1245184-…`.
- **Fix** (`scripts/e2e/chrome-handoff.mjs`): every range after the reconnect must start above 0, and together they must ask for at least the missing bytes and less than the whole file. A fresh download from zero still fails. The ranges and byte counts are recorded.
- **Local run (Windows, real Chrome):** S4 passed with exactly CI's pattern. 1,900,544 bytes kept; four ranges , , , ; 6,488,064 bytes requested = 6,488,064 missing. Verdict passed.
